# ADR-007 任务分解只做"提醒"，不做"闸门"

## 背景

阶段 0 评测确认三道失败题（R2 翻页 / R3 标签导航 / R4 搜索）有同一个缺失：
**系统里没有"任务进度"这个状态。**

每步喂给模型的是「goal + 当前快照 + 原始动作流水」，而流水是 `click e62` 这种原始记录。
模型要靠自己把「click e62 成功」翻译成「下一页已经翻过了」——
1.16s 就挂掉的 R2 干脆连 thought 都不写（15 tokens），12 步一路点到第 10 页。

review 代码时发现 `plan` / `progress` 的管道其实早就写好了：

- `workflow.py:179-180` 有字段、`:428` 有 `_absorb_plan()`
- `prompts.py` 有渲染 `[任务分解]` + `（已完成）/（未完成）`
- `workflow.py:276-277` 也传给了 `build_user_prompt`

但 `SYSTEM_PROMPT` 从来没让模型输出过这两个字段 → 永远是空 → `if plan:` 永远为假。
**一条铺好但没接水的管道。**

## 决定

接上这条管道，但**明确限定 plan 的地位：它只是提醒，不是必须走完的清单。**

四条边界：

| 编号 | 边界 | 落地方式 |
|---|---|---|
| 1 | plan 只在第一步给，之后不改 | `_absorb_plan` 里 `and not self.plan` —— 中途换计划会让已打的勾全部失效 |
| 2 | progress 只增不减 | 这轮没给有效序号就保留上一轮的；给 `[]` 不清空 |
| 3 | progress 只能指向 plan 里存在的条目 | 越界序号丢弃（旧写法 `max(len(plan), max(numbers))` 会放行"9 号挂在 3 条计划上"） |
| 4 | **plan 不得阻止 finish** | 硬规则 + 渲染文案 + 示例 4 三处一起写「信息够了立刻 finish，哪怕 progress 没填满」 |

第 4 条是这个 ADR 的核心，也是唯一一条**实测掉过分**的边界。

## 为什么要有第 4 条（实测证据）

第一版只写了「还剩 N 条未完成；全部完成后立刻 finish」。结果 **1/4**：

| 题 | 改前 | 改后 |
|---|---|---|
| R1 读第一条名言的作者 | ✅ 1 步 | ❌ 6 步 loop |
| R3 标签页第一条名言的作者 | ❌ 3 步答错 | ✅ 3 步答对 |

R1 的轨迹第 1 步：

```
s1 scroll    thought=第一条名言是'The world as we have created it is a process of o...
```

**答案已经写在它自己的 thought 里了**，但它选了 `scroll` —— 因为 plan 还剩两条没走完。
模型把「全部完成后立刻 finish」读成了硬闸门：计划没走完就不能结束，那就继续做动作。
于是一道一步题被 plan 拖成 6 步死循环。

补上第 4 条之后 R1 恢复、R3 保持，整体 **25% → 50%**。

## 后果

**好的部分**

- R3 从 0/3 变为通过，且步数从 3 降到 2（清单让它看清"还剩的是读作者，不是翻页"）
- R2 从「12 步 loop」变成「2 步落在正确页面」，失败形态从"打转"降级为"读错条目"
- 连跑两次结果完全一致，确定性未被破坏

**代价与遗留**

- 模型报 progress 的质量一般：R3 只报了 `[3]`、R2 一轮报 `[]`。机制上不崩，但勾不准
- plan 增加了 prompt 长度（这是本项目最稀缺的资源，见踩坑 #18）
- **R2 的剩余问题不在 plan 上**：它在正确的 page/2 上把第 9 条（Mark Twain）当成第一条。
  正文是一整块纯文本，10 条引言首尾相连，模型对不齐"引言 ↔ 作者"。
  修法在渲染层给正文加序号，与本 ADR 无关

**一条通用教训**

往提示词里加"清单/进度"类结构，风险不在它不生效，而在**它生效过头**。
清单天生带"没走完不能结束"的暗示，会盖掉"信息够了就停"这类更高优先级的判断。
凡是加这类结构，必须在同一批把「什么时候可以无视它」写清楚。
