## 2026-10-22 · venv 建不起来 / 虚拟环境解释器一启动就退出（exit 107）

**现象**

- `python -m venv .venv` 报 `ensurepip returned non-zero exit status 107`
- 改成 `--without-pip` 绕过 ensurepip 后，运行 `.venv/Scripts/python.exe` 报：
  `failed to open 'D:\????\chayixing\.venv\pyvenv.cfg'`
- 用 uv 分别以 Python 3.11 / 3.10 建 venv，现象完全一致

**定位过程**

1. 换解释器（系统 3.10.11、托管 3.13.12）都复现 → 排除 Python 版本问题
2. 看错误信息：路径里的「工程学习」变成了 `????` —— 非 ASCII 字符在传递过程中被按 ANSI 码页转换丢了
3. 同一台机器上，位于纯英文路径的解释器（`C:\Users\xr\AppData\Local\Programs\Python\Python310\python.exe`）能正常执行，只有放在项目中文目录下的 exe 起不来
4. 结论：不是 venv 或 pip 的问题，而是**执行位于中文路径下的 exe 时，路径在进程启动环节被破坏**

**根因**

运行环境的进程启动链路用 ANSI 编码传路径，中文被替换成 `?`；Python 启动时要读同目录的 `pyvenv.cfg`，路径坏了读不到，直接退出（exit 107）。*（具体是哪个环节做的转换未逐层验证，但「英文路径可跑、中文路径必挂」已被实验证死）*

**修法**

- 真实 venv 建在纯英文路径：`C:\Users\xr\.workbuddy\binaries\python\envs\chayixing`（用 uv 建）
- 项目根建 Windows 目录联接（junction）：`.venv` → 上述路径
- 本项目所有命令用英文绝对路径的解释器执行；用户在 VSCode 里用 `.venv` 不受影响

**副作用与注意**

- 项目目录换机器或改位置后，junction 需要重建
- 这不是项目代码的 bug，是工具链环境限制，不影响产品本身

## 2026-10-23 · 测试站筛选大小写敏感（用户实测发现）

**现象**

在列表页搜索框输入 `usb`，提示“没有匹配的商品”；输入 `USB` 才能搜到「USB 集线器」。

**定位过程**

1. 打开 `testsite/list.html`，看筛选逻辑：`products.filter(p => p.name.includes(kw))`
2. `String.prototype.includes` 是**大小写敏感**的字符串比较，`'USB 集线器'.includes('usb')` 为 false
3. 用户输入的是常见写法（小写），页面数据里是 `USB`，两边大小写不一致 → 过滤为空

**根因**

前端筛选没有做大小写归一化。属于测试站自身的 bug，不是 Agent 代码的问题。

**修法**

两边都转小写再比较：

```js
const kw = document.getElementById('keyword').value.trim().toLowerCase();
render(products.filter(p => p.name.toLowerCase().includes(kw)));
```

**验证**

用 Playwright 实跑四种输入：`usb` → 1 行（USB 集线器）、`USB` → 1 行、空 → 6 行、`键盘` → 1 行（机械键盘）。

**为什么这个 bug 要记**

测试站的 bug 会污染评测：T4（搜索任务）如果 Agent 行为完全正确，也会因为页面筛选大小写问题被判失败。**评测前先自测测试站本身**，否则数字是假的。

## 3. 提示词把"动作表"放最前面，模型在列表页绝不 finish

**现象**

T1「从首页进入产品列表，提取所有产品名称」，模型成功点进列表页（正文里 6 个商品名全在），随后：

- 第 1 版：连点 3 次「筛选」→ 被判 loop
- 第 2 版（加了"信息够就 finish"规则）：11 步来回点「返回首页」「筛选」、来回滚动 → 还是 loop

**定位过程**

1. 直接打印真实 prompt 与模型原始输出（不信猜测）：
   ```
   [正文] 产品列表 返回首页 筛选 名称 价格 分类 无线鼠标 ¥89 外设 机械键盘 ¥299 …
   模型输出：{"action": "scroll", "direction": "down"}
   ```
   快照里 6 个商品名清清楚楚，模型却去 scroll → 确认不是快照/截断的问题。
2. 做三种提示词写法的同输入对照实验（同一份快照，各调一次）：
   - 动作表前置 + 8 条规则 → `click e3`（无效动作）
   - 「先判断信息够不够 → 是就 finish」放最前，动作表压成一行一个 + 一句"读取类任务不需要点击" → **正确 finish**

**根因**

动作表放在最前面时，模型把它当成"菜单"，倾向于挑一个动作来"做点什么"。而读取类任务正确的动作恰恰是**什么都不做、直接给答案**。规则越多越稀释，8 条规则里"该 finish"那条被淹了。

**修法**

`prompts.py` 改成「判断优先」结构：第一段就是二选一（信息已在正文 → finish；否则才动），动作表一行一个，硬规则只留 5 条。

**验证**

T1 从 11 步失败变成 2 步成功。

## 4. 弱模型不听规则，few-shot 才管用

**现象**

T2 表单任务：填写完点提交，正文末尾已经出现「提交成功：姓名=张三…」，模型仍然连点 3 次「提交」被判 loop。

**定位过程**

1. 手工复现：确认提交真的生效、`提交成功：…` 确实进了快照正文（`form.html` 的 `#success` 由 `display:none` 变 block）
2. 把"页面新增内容"主动写进 prompt 后再跑 → **还是连点提交**，说明不是"它没看到"，是"它不会用"
3. 四组对照实验（同一 prompt、同一页面状态）：

   | 方案 | 输出 | 结论 |
   |---|---|---|
   | glm-4-flash + 加一条"见成功提示就 finish"的规则 | `click e6` | 规则无效 |
   | glm-4-flash + 一个 few-shot 示例 | `finish 提交成功：…` | **有效** |
   | glm-4.5-flash（换模型） | `finish 提交成功：…` | 有效，且自动带 thought |
   | glm-z1-flash（推理型） | `finish …`（带 `<think>` 块，需剥离） | 有效但更慢更啰嗦 |

**根因**

`glm-4-flash` 是指令遵循最弱的免费档，对"抽象规则"几乎不执行，但对"照着样子抄"很敏感。**同样一句话，写成规则没用，写成一个例子就有用。**

**修法**

系统提示词补 3 个 2~3 行的示例（提交表单 / 读表比较 / 搜索三步），比堆规则有效得多。

**验证**

T2 从 8 步 loop 变成 6 步成功；T3 从答错变成答对；T4 从"答 0"变成"答 1"。

## 5. 交替动作骗过了"连续重复"检测

**现象**

T5「详情页点下一页，取第二页标题」，模型在「下一页」和「上一页」之间来回跳，走满 12 步（step_limit），循环检测一次都没触发。

**定位过程**

1. 看 trace：`click e2 → click e1 → click e2 → click e1 …`
2. 查检测逻辑：只判断"最近 3 步是否同一个动作"，A B A B 里最近 3 步是 B A B，**三个不全相同**，判不出来

**根因**

页面上「下一页」和「上一页」是同一位置的两个链接，点来点去永远"有反应"，但页面在两页之间循环，任务原地踏步。这类死循环长成**周期为 2 的模式**，不是连续重复。

**修法**

`_is_looping()` 增加第二种形态：最近 4 步满足 `A B A B`（`last[0]==last[2] and last[1]==last[3] and last[0]!=last[1]`）也判 loop。

**验证**

T5 从 12 步 step_limit 变成 2 步成功；`tests/test_workflow.py` 补两条回归测试（连续重复 / 交替重复 / 正常推进不误判）。

## 6. 页面初始占位值被当成答案（T4 答 0）

**现象**

T4「搜索 usb，一共几条结果」，Agent 输入 `usb` 后**没点搜索**就 finish，答案是 `0`——它读的是页面初始的「共 0 条结果」。

**定位过程**

1. 看 trace：`type e2 <- 'usb'` → `finish '0'`
2. 对照 `search.html`：结果计数默认渲染成「共 0 条结果」，只有点按钮才重算

**根因**

模型把"动作执行前的初始占位文本"当成了事实。真实站点上这种占位更普遍（"暂无数据""加载中""0 条结果"），属于通用陷阱，不是测试站特有。

**修法**

搜索类示例改写成**连续三步**（输入 → 点搜索 → 结果更新后才 finish），并在提示词末尾加一句：
「页面上的「共 0 条结果」可能只是初始值，动作执行前不要拿它当答案。」

**验证**

T4 从"答 0"变成 3 步、答案 `1`（正确）。

## 7. 前端代理漏了一条路径，Agent 把"我自己的界面"当成了目标页面

**现象**

M5 前端第一次联调：选 T4（搜索 usb 报条数），界面显示「已完成」，答案 `1`——看起来全对。
但轨迹里的截图不对劲：截的不是商品搜索页，而是 **WebPilot 自己的界面**（左边有任务表单）。

**定位过程**

1. 看截图 → 确认页面不对（这是最快发现问题的信号，文字和数字都可能"碰巧对"，像素不会骗人）
2. 查 start_url：`http://localhost:5173/testsite/search.html` —— **5173 是 Vite，不是后端 8000**
3. 打开 `curl http://localhost:5173/testsite/index.html` → 返回的是 SPA 的 index.html，不是测试站
4. 查 `vite.config.ts`：proxy 只配了 `/api` 和 `/runs`，**没配 `/testsite`**
5. 推论成立：Vite 对未知路径按 SPA 规则回退 `index.html`，于是 Agent 在自己的界面里"搜索"，读到了界面上的文字，还凑巧给出了一个看起来合理的答案

**根因**

前端用 `window.location.origin` 拼默认起点，而前端 dev server 与后端**不同源**；
"哪些路径归后端"这件事只存在于 `vite.config.ts` 的 proxy 表里，是**隐式契约**——漏一条就静默走错。

**修法**

```ts
proxy: {
  "/api": ..., "/runs": ...,
  "/testsite": { target: "http://127.0.0.1:8000", changeOrigin: true },
  "/docs": ..., "/openapi.json": ...,   // 顶栏「接口文档」同理，漏了就掉回自己
}
```

**验证**

`curl http://localhost:5173/testsite/index.html` 返回「WebPilot 测试站」；重跑 T4 → 3 步、答案 `1`、截图显示真正的搜索页。

**两个教训**

1. **`success` 是"模型说完成"，不是"做对了"**。这次任务"成功"且答案正确，但过程完全跑偏——只能靠看截图发现。M6 的评测必须带答案校验 + 关键步骤校验，只看 status 会得出假数字。
2. 域名白名单管不住这种事：`localhost:5173` 也在白名单里，它确实是"本地"。**白名单要能到端口/路径级别**，否则"允许 localhost"就等于"允许我自己这台机器上的一切"。

## 8. 评测跑出 100%，但那是"题太简单"，不是"Agent 强"

**现象**

M6 首轮正式评测：5 任务 × 3 轮 = 15 次，**15/15 全过**，平均 3.2 步、8.5s。
数字漂亮得不像话——一个免费弱模型 + 3 个示例，怎么可能 100%。

**定位过程**

1. 逐个看样本构成：T2（填表提交）≈ 示例 1，T3（读表筛价格）≈ 示例 2，T4（搜索计数）≈ 示例 3
   —— **评测集和提示词同源**，测的其实是"它记住例子了没有"
2. 看页面复杂度：单页、无异步加载、无登录、无弹窗、元素不超过 6 个
3. 于是设计三个**分布外**探针（`scripts/eval_probe.py`）：
   - 两步子任务：先搜 键盘 记数，再搜 鼠标 记数
   - 反向指令：只填姓名、明确禁止提交
   - 页面上没有排序功能的推理：自己比较所有价格找最贵

**结果**

| 探针 | 结果 | 说明 |
|---|---|---|
| 排序推理 | pass | 答案 显示器 ¥1299，正确（中间还瞎点了筛选、滚了两次，但读正文读对了） |
| 部分填写不提交 | pass | 答案「李四」，且没有触发提交 |
| 连续两次搜索 | **fail** | 只做了第一次搜索（键盘→1 条），第二次输入完没点搜索就拿 1 当答案 |

泛化通过率 **2/3 = 67%**，跑两次结果一致。

**根因**

失败形态非常一致：**多步子任务被压成一步**。模型把"搜两次"理解成"搜一次然后回答"，
因为提示词里唯一的多步示例（示例 3）只演示了"输入 → 点搜索 → finish"，
没有演示"再做一轮"。

**修法（P1 内不做，记下）**

- 评测集必须与提示词隔离：正式评测要留一部分任务**永远不进 few-shot**
- 100% 是危险信号。**评测跑满分别先怀疑评测集，再高兴**
- 多步子任务需要单独的提示结构（比如要求先输出"子目标清单"再逐个完成），不是加一条规则能解决

**为什么这条比"100%"更重要**

对外汇报时，"15/15" 是个漂亮但空洞的数字；能说清"为什么它其实只值 67%、失败长什么样、下一版怎么补"，
才是真正做过这件事的证据。

## 9. 加固提示词连续两次掉分：70% → 60% → 60%

**现象**

隔离集基线 70%（10 任务，两轮 20 次，失败点完全固定：H3 去重、H4 筛选、H6 往返）。

想加固，加了东西，结果**都更差**：

| 版本 | 改动 | 结果 |
|---|---|---|
| v1 | 基线 | 70%（14/20） |
| v2 | 加【多步任务】plan/progress 结构 + 统计规则 + 筛选规则（约 400 token） | 60%（12/20） |
| v3 | v1 + 两条针对机制的短规则（"跳转后编号重排"、"搜索是两步"，共 2 行） | 60%（12/20），且**原本通过的 H1 变成 loop** |

**定位过程**

1. v2 掉分后先怀疑实现有 bug → 诊断 H4/H6 单跑：
   - H4：点筛选（空关键词，无效）→ 输入"配件" → **没再点按钮**就 finish，拿全表当答案
   - H6：trace 显示 `click e2 → e1 → e2 → e1`，且 thought 说"现在需要点下一页"却在点 e1
     → 跳转后编号重新分配（detail2 的 e1 是「上一页」），它沿用了上一页的编号
   → 说明这两条要修的机制**判断是对的**
2. 于是 v3 只加两行短规则，结果还是 60%，还把 H1 弄成 loop
3. 三次数据摆一起，规律只有一个：**提示词越长，表现越差**

**根因**

`glm-4-flash` 的指令遵循"预算"极小。模型不是"没看懂那条规则"，是**新增文字挤占了注意力**：
同一份快照里，它把"记得对照 plan"和"记得重新读编号"都丢掉了，连原本能过的计数题也开始乱点。

**修法**

回滚到 v1，把加固方向改成**代码层兜底**（见 ADR-005）：
- 编号漂移 → 动作校验时比对目标元素 text，变了就回喂"编号已重排"
- 多步缺失 → 检测"输入框 value 变了但页面正文没变"这种形态，明确告诉它"还差一步点按钮"

**教训**

1. 提示词改动必须跑隔离集回归，**单次"看着变好了"不算数**（v3 的两条规则单看都很合理）
2. 弱模型上"加规则"几乎总是负收益，正确方向是"减少它需要记住的东西"——宁可写成代码
3. 有一把稳定的尺子（失败点每次都一样），才敢下"这是回退不是噪声"的结论

## 10. HuggingFace 下模型：镜像配了也 401，因为镜像不代理 Xet

**现象**

`WhisperModel("small", ...)` 首次加载要下模型，直接报：

```
httpx2.ProxyError: 502 Bad Gateway
  File "...\huggingface_hub\hf_api.py", line 3188, in model_info
```

按常识加上国内镜像 `HF_ENDPOINT=https://hf-mirror.com` 后，前半段通过了，但换成另一个错：

```
RuntimeError: Task error: File reconstruction error: CAS Client Error:
  HTTP status client error (401 Unauthorized),
  domain: https://cas-server.xethub.hf.co/v2/reconstructions/429ffc...
```

**定位过程**

1. 先确认不是 key 问题：faster-whisper 用的是公开模型（`Systran/faster-whisper-small`），不需要 token
2. 看错误域名的变化：从 `huggingface.co` 变成 `cas-server.xethub.hf.co` —— **域名换了**，说明请求被重定向到了另一套存储
3. 查证：`xethub` 是 HuggingFace 新上的分块存储后端（Xet），大文件走它、不走常规 CDN
4. 关键推论：镜像站转发的是 `huggingface.co` 的请求，但它**没有实现 Xet 协议**；
   SDK 拿到 Xet 地址后直连官方域名 → 国内直连 401 / 超时
5. 验证：关掉 Xet（`HF_HUB_DISABLE_XET=1`）让它回退普通 HTTP 分块下载，一次成功

**根因**

`HF_ENDPOINT` 只替换了 API 入口，**没有替换 Xet 存储域名**。SDK 会先问索引"这个文件怎么下"，
索引回答"走 Xet"，于是请求跳到 `cas-server.xethub.hf.co`——镜像不在这条链路上。

**修法**

两个变量必须一起设，缺一个都不行：

```python
os.environ.setdefault("HF_ENDPOINT", "https://hf-mirror.com")
os.environ.setdefault("HF_HUB_DISABLE_XET", "1")
```

写在 `app/voice/asr.py` 模块顶部，且**必须在 `import faster_whisper` 之前**——
`huggingface_hub` 在 import 期就会把环境变量读成常量，之后设置不生效。

**教训**

1. 「配了镜像还失败」不一定是镜像挂了，要看**报错域名有没有变**；域名一变就说明绕过了镜像
2. 环境变量要在**代码里设 setdefault**，不能只写在 shell 或 README 里——换个终端就复现故障
3. 这个坑的排查成本远高于它本身的技术含量：现象是 502/401，看起来像网络，实际是协议协商

## 11. 用普通 Lock 包住会再取锁的函数 → 永久死锁，无报错无日志

**现象**

（写代码时自查发现，未进测试）`asr.transcribe()` 先 `with _lock:`，然后在锁内部调用
`_load_model()`，而 `_load_model()` 自己也要 `with _lock:`。
请求发出后 HTTP 一直挂着不返回，没有异常、没有 traceback，服务端口照常监听、`/health` 照常 200。

**定位过程**

1. 读代码时发现同一条调用链上出现了两次 `acquire` 同一把 `threading.Lock`
2. 回忆语义：`threading.Lock` **不可重入**——同一线程第二次 acquire 会阻塞，等于自己等自己
3. 对照现象：这种死锁不会抛任何错，只有一个"卡住的请求"，所以最难和"慢"区分

**根因**

`Lock` 只记录"锁被占用"，不记录"被谁占用"。所以重入时它无法识别"占用者就是我"，只能等。

**修法**

改成 `threading.RLock()`（可重入锁，记录持有线程），同线程重入直接放行。
并在两处都写了注释互相指认，避免以后有人"优化"回 Lock。

```python
_lock = threading.RLock()      # 见 asr.py：transcribe 持锁后会再进 _load_model
```

**教训**

1. 一把锁跨越两层函数时，必须先问"这两层会不会在同一线程里嵌套"
2. 死锁的表现是**静默挂起**，不会报错。所以线程/锁相关的代码不能只靠跑测试发现，
   要么读一遍调用链，要么加超时（`acquire(timeout=...)`）
3. 能用"单例 + 只在慢路径抢锁"（双检）就别让锁横跨调用层

## 12. 按下立刻松手，录音却一直录到上限

**现象**

（虚拟麦克风实测发现）快速点一下麦克风按钮（松手早于权限弹窗返回），按钮变成"正在录音"，
并且**一路录到 30 秒上限**才自己停。用户视角是"我就点了一下，它自己录了半分钟"。

**定位过程**

1. 看事件顺序：`onMouseDown` → `startRecording()` 是 async 的，第一步 `await getUserMedia()`
   要等权限/设备初始化（几十到几百毫秒）
2. `onMouseUp` 在这个 await 还没返回时就触发了 `stopRecording()`
3. 此刻 `recorderRef.current` 还是 `null`（MediaRecorder 尚未创建），
   `recorderRef.current?.state === "recording"` 为假 → 函数直接 return，**什么都没做**
4. 之后 `getUserMedia` 返回、recorder 创建并 start —— 已经没有人再来停它了

**根因**

"用户要停"这个意图发生在"能停的对象"存在之前，被丢掉了。
本质是**异步创建对象 + 同步处理停止**的竞态。

**修法**

加一个 `pendingStopRef` 记下"用户已经松手"：

```tsx
const stopRecording = () => {
  if (phase === "starting") { pendingStopRef.current = true; return; }  // 记下来
  if (recorderRef.current?.state === "recording") recorderRef.current.stop();
};

// startRecording 里，recorder.start() 之后：
if (pendingStopRef.current) {
  pendingStopRef.current = false;
  window.setTimeout(() => { /* 120ms 后补一次 stop */ }, 120);
}
```

延 120ms 是为了让 MediaRecorder 至少吐一个 chunk，否则 blob 是 0 字节，
连"太短"都判不出来，会变成空上传。

**教训**

1. **"按下/松手"这类成对事件，必须能处理"另一头还没准备好"的情况**。
   凡是 `onDown` 里 await 过任何东西，`onUp` 都要假设对象还不存在
2. 补丁要考虑"来不及"：只记 flag 不够，还得等数据真的产出了再停，否则拿不到音频
3. 这类竞态在真人手上偶发（手快才踩到），必须用虚拟设备/自动化构造，靠手点很难复现

## 13. whisper 在非语音音频上"幻听"，会凭空造出句子

**现象**

（虚拟麦克风实测）Chromium 假设备输出的是合成提示音，不是人声。转写结果却不是空，
而是：

```
字幕製作人Zither Harp
```

一句完全不存在、还带繁体中文和英文的句子。

**定位过程**

1. 先怀疑代码把音频截断/拼错了 → 用同一份 mp3 直接跑 `model.transcribe()`，结果一致
2. 已开 `vad_filter=True`（静音检测），但仍出幻觉 → 说明问题不在"静音没切掉"
3. 本质原因在模型行为：whisper 训练数据里有大量带字幕的视频音频，
   遇到"有能量但不是语音"的输入时，它会优先输出**字幕署名/音乐标记**这类高频短语

**根因**

whisper 是"必须产出文本"的模型——它没有"我确定这不是语音，所以返回空"这个动作。
VAD 只能过滤低能量段，挡不住"有能量的噪音"。

**修法**

代码层没法根治，只能**产品层兜住**：

1. 转写结果**只填进输入框、绝不自动提交**，必须让用户看一眼
2. 空文本时返回友好提示（"没听清，再说一次"）而不是报错
3. 后端对极短音频（<1KB）直接拒绝，不进模型

**教训**

1. 这条是"ASR 一定会错字"的实证——同音字（扩展坞 → 扩展物）、繁体、英文都有。
   **任何"语音直接触发动作"的设计都是危险的**，尤其当动作是提交表单或提交订单
2. 模型没有"我不知道"这个输出，就要在系统层面给它加一个
3. 别用"转写准确率"当唯一指标，要看"错误发生后用户能不能发现并纠正"——这才是可用性

## 14. 失败播报把开发者的诊断信息念给了用户听

**现象**

用失败任务测播报接口，返回的待朗读文本是：

```
任务卡住了，在原地打转，我主动停了下来。连续 3 次相同动作：click e1
```

`click e1` 会被念成"click 一"。

**定位过程**

1. 原始实现为了"信息完整"，把 `meta.note` 直接拼在状态文案后面
2. 但 `note` 的来源是 workflow 的归因逻辑，写给人**看**的：
   含英文动作名、元素编号、`e1` 这种内部标识
3. 同一句话在界面上以文字显示时完全可读，念出来就是噪音

**根因**

把"给人看"的字符串当成了"给人听"的字符串。
这两种媒介的约束不同：**眼睛能跳读、能忽略括号里的技术细节；耳朵不能。**

**修法**

`_speech_text()` 只返回两类内容：有答案念答案，没答案念一句口语化的状态。
**不拼 note**。界面上的 `note` 照常显示，细节留给眼睛。

```python
def _speech_text(meta):
    if answer: return answer
    return _STATUS_SPEECH.get(status, "任务没有给出结果。")   # 不拼 note
```

并写了回归测试 `test_speech_never_reads_diagnostic_note` 钉死这个行为。

**教训**

1. 语音不是"把文字念出来"，是**另一种输出通道**，需要自己的文案层
2. 凡是给用户"听"的内容，要额外检查：有没有英文标识符、编号、括号、缩写
3. 这个 bug 只有真去听才会发现——所以语音功能的验收标准里必须有"听一遍"

## 15. 在 IDE 预览面板里点麦克风：永远"没有权限"，且不弹授权框

**现象**

用户在 IDE 的内置预览面板里点「语音输入」，直接提示没有权限。
去浏览器设置里找这个站点，**找不到**——好像从来没申请过。
但同一份代码，用 Playwright 起真实 Chromium 跑，录音→上传→转写全通。

**定位过程**

1. 先排除系统层：查 `HKLM:/.../CapabilityAccessManager/ConsentStore/microphone` → `Allow`
2. 排除组策略：`HKLM:/SOFTWARE/Policies/Microsoft/Edge`、`...\Google\Chrome` 都不存在
3. 排除代码：真实 Chromium（含虚拟音频设备）跑通，说明 `getUserMedia`、
   `MediaRecorder`、上传链路都没问题
4. 剩下唯一的变量就是**运行环境**：区别在于"页面是顶层文档还是被嵌进去"
5. 复现：写一个父页面用 `<iframe src="http://localhost:5173">` 嵌住应用 → 现象完全一致

**根因**

`getUserMedia` 在 iframe 里属于**权限策略（Permissions Policy）管辖的强能力**，
必须由父页面显式授予（`<iframe allow="microphone">`）。
没授权时浏览器**立刻拒绝，不弹框、不记录站点权限**——
所以用户在浏览器设置里根本看不到这个站点，无从放行。

这也是"没权限"和"被拒绝"的区别：被拒绝是用户点过"阻止"，能改；
没授权是浏览器的策略层直接拦下，用户侧无解。

**修法**

代码层做两件事，让它自己说出病因：

1. 检测嵌入：`window.self !== window.top`（跨域访问 `window.top` 会抛异常，抛了也算嵌入）
   - 提前在按钮下方常驻提示，而不是等用户点了才报错
   - 点击时直接拦截并给出"换个入口"的解法，不去调用必然失败的 `getUserMedia`
2. 错误提示**保留浏览器原始错误名**（`[NotAllowedError]` / `[NotFoundError]` / `[NotReadableError]` / `[SecurityError]`）
   - 这四种的原因和修法完全不同，只显示中文"没有权限"的话永远分不清

**教训**

1. **"没权限"是个筐，至少装了四种病**：用户拒绝 / 系统禁用 / 嵌入无授权 / 非安全上下文。
   错误提示里丢掉原始错误名，等于把诊断信息也一起丢了
2. 开发期一定要用**真实浏览器**验证一遍涉及系统能力的 API（麦克风、摄像头、剪贴板、通知）。
   自动化测试跑通不代表用户点得通，因为环境不一样（顶层 vs 嵌入）
3. 凡是"预览/嵌入"的宿主环境，都要假设受限。产品上正确的做法不是"教用户去改设置"，
   而是**明确告诉他换个入口**——因为嵌入场景下用户改不了

## 16. 浏览器不走系统代理：curl 3 秒能开的站，Agent 20 秒超时

**现象**

走出测试站的第一步就撞墙。同一个 URL，几乎同一时间：

| 方式 | 结果 |
|---|---|
| `curl https://books.toscrape.com/` | ✅ 200，3.5 秒 |
| Agent 的 Playwright Chromium | ❌ `Page.goto: Timeout 20000ms exceeded` |

任务状态 `nav_failed`，步数 0，耗时 21.34 秒（正好是 `NAV_TIMEOUT_MS`）。
第一反应是"目标站点挂了"或者"网络不稳定"——但 curl 明明通。

**定位过程**

1. 先看 meta.note 拿到真实异常：`TimeoutError: Page.goto: Timeout 20000ms exceeded`
   → 排除白名单（白名单不过会报 `域名不在白名单`）、排除代码异常
2. 打印环境变量，发现机器上有本地代理：
   ```
   https_proxy=http://127.0.0.1:62723
   http_proxy=http://127.0.0.1:62723
   ```
3. 关键认知：**curl 读这两个环境变量，Chromium 不读**。
   Chromium 读的是操作系统（注册表 / 系统设置）的代理配置。
   很多代理工具只设环境变量，不改系统设置
4. 验证：给 Playwright 的 `launch()` 显式传 `proxy={"server": ...}` → 8.0 秒打开
5. 结论：不是网络问题，是**浏览器进程根本没走代理**

**根因**

`launch(proxy=...)` 是浏览器进程级参数，不传就直连。
`HTTP_PROXY` / `HTTPS_PROXY` 这类环境变量是 Unix 世界的约定，
被 curl / requests / Go 等工具遵守，但 Chromium 走自己的系统设置读取路径。

**修法**

在 `browser/session.py` 里加 `_proxy_config()`：优先读 `.env` 的 `BROWSER_PROXY`，
没配就回退到环境变量，都空则直连。传给 `chromium.launch(proxy=...)`。

```python
launch_kwargs = {"headless": self._headless}
proxy = _proxy_config()          # .env > 环境变量 > 直连
if proxy is not None:
    launch_kwargs["proxy"] = proxy
self._browser = await self._pw.chromium.launch(**launch_kwargs)
```

配套两个细节：
- `BROWSER_PROXY=direct` 表示强制直连（代理坏了但本地测试站还要跑时用）
- 大小写都要查（`HTTPS_PROXY` / `https_proxy`），不同工具设的大小写不一样

**⚠️ 一个反直觉的副作用（实测踩到）**

第一版加了 `bypass="127.0.0.1,localhost"`，想防止代理把本地测试站也拦掉。
结果**真实站点反而打不开了**（20~25s 超时），而本地站点正常。
去掉 bypass 后真实站点恢复。多组对照（无 bypass / 127+localhost / 加 ::1 / `<-loopback>`）
数据离散度极大，说明这个参数在这里是干扰项——**Chromium 本来就隐式绕过回环地址**，
不需要显式写。最终结论：不要加 bypass。

**教训**

1. **"同一个 URL，一个工具通一个工具不通"时，第一件事是比"两者的网络出口是否相同"**，
   而不是怀疑目标站点
2. 涉及外部网络的排查，必须确认"代理/证书/网关"这三层是不是都对齐了
3. 加一个"看起来更保险"的参数（bypass）反而引入了新故障。
   对照实验的价值就在这里：不加参数反而是对的
4. 这类问题在**用户机器上大概率也存在**——凡是跑在公司网络/代理环境下的浏览器 Agent，
   都会遇到同一堵墙

## 17. 服务刚启动就下单，任务 1.16 秒猝死：`partially initialized module 'httpx2'`

**现象**

第三次复测的**第一题第一轮**，任务在 1.16 秒就变成 `error`，连浏览器都没起来
（`runs/` 下该任务目录里只有 `meta.json` + 空的 `trace.json`，一张截图都没有）：

```
AttributeError: partially initialized module 'httpx2' has no attribute 'URL'
(most likely due to a circular import)
```

这个错误长得像"依赖装坏了"，很容易被当成环境污染去重装包 —— 但同一条命令
下一轮就正常了，说明它是**时序相关**，不是环境坏了。

**定位过程**

1. 先确认 `httpx` / `httpx2` 两个包都在，`import httpx2` 单独跑完全正常
   （`hasattr(httpx2, 'URL')` → True）→ 排除依赖损坏
2. 查谁 import `httpx2`：只有 `huggingface_hub`（`file_download.py:16` / `hf_api.py:37` /
   `errors.py:6`）和 `starlette.testclient`（仅测试用）。`openai` 用的是 `httpx`，不是它
3. 结论：**唯一会在启动瞬间 import `httpx2` 的，是 ASR 模型预热的那个后台线程**
   （`faster_whisper.utils` → `huggingface_hub.snapshot_download` → `httpx2`）
4. 装上 import 钩子做探针，记录"哪个线程、从哪一行 import 了 httpx2"：
   ```
   httpx2 | MainThread | app/main.py:52 <- app/voice/asr.py:112
   httpx2 | asyncio_0  | huggingface_hub/_snapshot_download.py:5
   httpx2 | asyncio_0  | huggingface_hub/file_download.py:16
   httpx2 | asyncio_0  | huggingface_hub/hf_api.py:37
   ```
   修复后：MainThread 先完整加载完，后台线程全是缓存命中
5. 试了 20 次"两个线程同时从零 import `httpx2` 和 `huggingface_hub.file_download`"
   → **0 次复现**。说明机制不是"两线程抢 import"，而是"模块正处在半初始化状态时
   有人取它的属性"

**根因**

`huggingface_hub/errors.py` 用的是 `from httpx2 import HTTPError, Response`。
如果这一刻 `httpx2` 的模块体还没执行完（`sys.modules` 里存着半成品），
取 `httpx2.URL` 就会报 "partially initialized"。

而"半初始化"只在**首次 import 恰好与另一个线程的首次 import 重叠**时出现，
窗口是毫秒级 —— 所以它只在"服务刚起 1 秒内就有人下单"时偶发。

**修法**

不是加锁，而是**让 import 只在一个线程里发生**：
`lifespan` 里先在主线程同步 `asr.preload_import()`，再开后台线程去加载模型。

⚠️ **我第一版修错了**：只写了 `import faster_whisper`。依赖链是分层的：

```
faster_whisper            ← 外壳，不含下载逻辑
  └ faster_whisper.utils  ← :7  import huggingface_hub
      └ huggingface_hub.file_download / hf_api  ← :16  import httpx2
```

裸 `import faster_whisper` 后两层一层都没走到，等于没预载。改成三行：

```python
import faster_whisper        # 外壳
import faster_whisper.utils  # 真正的下载路径
import httpx2                # 竞态的受害者，在主线程压平它
```

**验证的诚实边界**

- ✅ 能做实的：探针证明 MainThread 在任何线程启动前已完整执行完 `httpx2` 模块体
- ✅ 能做实的：修复后零间隔下单（端口就绪后 32ms 发请求，此时模型仍在加载）→ 任务 success
- ❌ 做不到的：**关掉修复跑 3 次负向对照，一次都没复现原 bug**。
  触发条件是概率性的，我没有可靠的复现手段

所以这里的结论只能写成：**"半初始化"这个前提条件被消除了，不是"复现→修复→复现消失"的闭环**。
这条边界必须写下来，否则以后有人看到"已修复"会误以为有测试兜着。

**教训**

1. **"partially initialized module" 一定要理解成"时序"，不要理解成"依赖坏了"**。
   前者重装包没用，后者才是重装
2. **预载重模块要沿着依赖链一路到底**。只 import 最外层包装，等于什么也没做——
   而它又有"看起来修了"的错觉，比没修更危险
3. 修 bug 后要明确区分「机制上确定性成立」和「实测复现消失」。
   前者可以说"已加固"，后者才能说"已验证修复"

## 18. 一个图例符号 + 一段 1065 字符的报错，把 prompt 挤掉了 87%

**现象**

走出测试站后，R4（"这个页面上第一条名言的作者还写过哪些书"）失败得很怪：

```
e24 是 link，不能输入文字
```

模型说"是 link 不能输入"，听起来像是在讲道理。但复查轨迹发现两件事：
`e24` 的真实文本是 `Skip to search`，位置 `y = -320`（`in_viewport = False`）。
模型不是不会判断 —— 它压根没看出这个元素在屏幕外。

**定位过程**

1. 看快照渲染代码，元素行是这样拼的：

   ```
   [可交互元素] 共 42 个（* = 在视口内）
     e24  link     Skip to search
   ```

   "在视口内"用的是**星号约定**。于是模型要先做两步：
   `记住 "（* = 在视口内）" 这条图例` → `检查行内有没有星号`。
   弱模型（GLM-4-Flash 这个量级）在第二步就放弃了，直接把 `e24` 当成可操作元素
2. 顺手量了一下喂给模型的 user prompt 长度：**1191 字符**。
   拆开看，最大的一块是 history 里原样塞进去的 Playwright 报错：
   一次点击超时的 Call log 有 **27 行、1065 字符**，其中 95% 是
   `waiting for element to be visible, enabled and stable` 这类复读
3. 两个问题其实是同一个问题的两面：**prompt 是稀缺资源**。
   图例占位置、长报错占位置，挤掉的都是真正有用的信息（元素列表）

**根因**

1. **要求模型"先记符号再解码"的写法，在弱模型上等于没写**。
   符号是给人省地方的，对模型是额外的推理步骤 —— 应该让标记自解释
2. **原始报错是给开发者看的，不是给模型看的**。
   1050 字符里有用的只有一句"元素在视口外，点不到"

**修法**

1. `snapshot.py`：删掉图例，改成只在需要的元素后面加自解释标记

   ```python
   head = f"[可交互元素] 共 {total} 个"        # 图例整句删除
   ...
   if el.get("in_viewport") is False:          # 注意是 is False，不是 falsy
       parts.append("[屏外]")
   ```

   为什么用 `is False` 而不是 `if not el.get(...)`：字段缺失（None）和"确认不在视口"
   是两件事。None 时不该打标记，否则会把不确定说成确定。
2. `prompts.py`：加 `short_error()`，把报错压成一句人话再进 history

   ```python
   _ERROR_PATTERNS = [
       ("outside of the viewport", "元素在视口外，点不到（先 scroll，或换一个元素）"),
       ("intercepts pointer events", "元素被别的东西挡住了（可能有弹窗/遮罩）"),
       ...
   ]   # 顺序有意义：先匹配具体原因，再落到"报错第一行"
   ```

   完整报错仍然留在 trace 里（排查要用），只有拼 prompt 时才压缩。

**效果（这是本次唯一能量化的部分）**

```
修复前 prompt：1191 字符
修复后 prompt： 157 字符
减少 1034 字符（-87%）
```

**诚实的边界**

prompt 变短是**确定可测**的；成功率有没有因此提升，**这次测不出来**。
实测三轮成功率没变（25% → 25%）——原因不是"改了没用"，而是这几处修的是
可观测性和输入卫生，而剩下的失败卡在"任务进度判断"上。
完整分账见 `docs/阶段0-真实站点评测.md` 第四节。

**教训**

1. 写 prompt 时，凡是需要"先记规则、再应用规则"的设计，都要怀疑它在弱模型上会失效。
   **能自解释就别用符号**
2. trace 里留全文、prompt 里放摘要 —— 两个受众（人 / 模型）要分开伺候
3. 一个"顺手量一下"的动作（数 prompt 多少字符）往往比翻十页日志更能定位问题

## 19. 加了「任务分解」，R3 从 0 分变满分、R1 从满分变 0 分

**现象**

给 Agent 加 plan/progress（把任务拆成子目标、每步标记完成）之后，
第一轮复测的结果是 1/4：

| 题 | 改前 | 改后 |
|---|---|---|
| R1（读第一条名言的作者） | ✅ 1 步答对 | ❌ **6 步 loop** |
| R3（标签页第一条名言的作者） | ❌ 3 步答错 | ✅ 3 步答对 |

**一换一，净收益为零。** 而且崩的是最简单的那道题。

**定位过程**

读 R1 的轨迹，第 1 步的 thought 是这样的：

```
s1 scroll    thought=第一条名言是'The world as we have created it is a process of o...
s2 click e1  thought=找到第一条名言
s3 click e1  thought=找到第一条名言的作者信息    ← 点进作者页，els 从 55 掉到 4
s4 click e3  thought=找到第一条名言，现在需要找到作者信息
s5 click e1  →  s6 click e3                    ← A B A B 循环
```

关键在第一行：**它已经把答案写在自己的 thought 里了**，但它没选 `finish`，选了 `scroll`。

它给自己定的 plan 是 `['找到第一条名言', '找到作者信息']`，
而我在渲染里写了一句「还剩 2 条未完成；**全部完成后立刻 finish**」。

模型把这句话理解成了**硬闸门**：计划没走完 → 不能 finish → 那就继续做动作。
于是它为了"走完 plan"，去点开作者页；作者页上当然也没有「第一条名言」，再点回来……
一个本来一步就能答完的题，被 plan 拖成了 6 步死循环。

**根因**

不是 plan 这个概念错，是我给它的**优先级关系**错了。
系统提示词开头写的是「第一步永远是判断：信息够了就 finish」，
但它在 plan 那条规则面前失效了 —— 因为「全部完成后立刻 finish」读起来更像一条硬约束，
而且它离决策点更近（在 prompt 里更靠后、更具体）。

**修法**

三处一起改，都围绕"plan 是提醒不是闸门"：

1. 硬规则里把定位写明：
   `plan 只是提醒自己别漏步骤，不是必须走完的清单。只要正文里已经能看到答案，
   立刻 finish —— 哪怕 progress 还没填满`
2. 渲染的那句改成：
   `还剩 N 条未完成。plan 只是提醒，不是必须走完的清单：现在就能回答任务的话，直接 finish。`
3. 加**示例 4**，直接对着失败场景写：给了 plan、刚点完下一页、而正文第一条就写着作者名
   → 正确输出是 `finish` 而不是"再看看"

改完 R1 恢复 1 步答对，R3 保持通过，整体 **25% → 50%**。

**教训**

1. **往提示词里加"进度/清单"类结构时，最大的风险不是它不生效，而是它生效过头**。
   清单天然带着"没走完就不能结束"的暗示，会盖掉"信息够了就停"这类更高优先级的判断。
   凡是加这类东西，**必须同一批把"什么时候可以无视它"写清楚**
2. **一条规则的分量不只取决于措辞，还取决于它在 prompt 里的位置**。
   系统提示词最前面写的总原则，会被后面更具体、更贴近动作的规则压过。
   这不是模型"没读懂"，是它把更具体的指令当成了更近的约束
3. **一次改一处，看一轮结果**。第一轮 1/4 时如果继续在别处加东西，
   就永远分不清是 R1 退化和 R3 提升各自来自哪一句
4. 这个项目上「加提示词 → 掉分」已经第三次了（#3 动作表前置、#9 加固连掉两轮、本条）。
   结论已经够稳定：**在这个模型上，提示词改动的效果不可预测，必须每改必测**

## 20. 正文被压成一行 + 截断位置恰好切掉唯一答案 → 模型读了第 9 条当第一条

**现象**

R2（点下一页，报新页第一条名言的作者）在 plan/progress 修好之后，不再打转了：
2 步就落在正确的 page/2 上。但它给出的答案是 **Mark Twain**，而正确答案是 **Marilyn Monroe**。

`curl` 确认 page/2 的作者顺序是：Marilyn Monroe / J.K. Rowling / Albert Einstein /
Bob Marley / Dr. Seuss / Douglas Adams / Elie Wiesel / Friedrich Nietzsche / **Mark Twain** / Allen Saunders。

**Mark Twain 是第 9 条**。模型在轨迹里写的是「已经在第2页，正文第一条就写着 by Mark Twain，读到了」——
它不是猜的，是**真的以为自己看到了第一条**。

**定位过程**

1. 把浏览器开起来，直接 dump 快照的正文，先看形态：

   ```
   截断=True | 长度=1216 | 行数=1
   L1| "Quotes to Scrape Login “This life is what you make it. No matter what, you're go"
   ```

   **整页只有 1 行**。引言、作者、标签、页码全被压成一条 1216 字符的长虫。
2. 找到源头，`snapshot.py` 里取正文的那一行：

   ```js
   const rawText = (document.body.innerText || '').replace(/\s+/g, ' ').trim();
   ```

   `\s+` 不只压空格，**换行也一起压掉了**。`innerText` 本来保留了页面结构，
   被这一行抹平 —— 这是"想省 token 反而变蠢"的典型。
3. 第二层问题：截断策略是"头 60% + 尾 40%"，中间插一句省略提示。
   把不截断的全文量出来（`max_text_chars=100000`）：

   | 位置 | 内容 |
   |---|---|
   | 全文长度 | 3445 字符 |
   | **1108** | `by Marilyn Monroe` ← R2 的答案 |
   | 1299 | `by J.K. Rowling` |
   | **3079** | `by Mark Twain` ← 它答出的那个 |

   上限 1200 → 头部只有 720 字符 → **答案在 1108，被切在外面**；
   尾部从约 2965 开始 → `by Mark Twain` 在 3079，**正好是拼接后的第一句**。
   于是模型看到"头部（第一条引言被切断）＋ 紧跟着 by Mark Twain"，
   非常合理地判断成了"正文第一条 = Mark Twain"。
4. 关键认知：**这不是"截断丢了一点信息"，是"截断位置恰好切断了唯一答案"**。
   前者的代价是模型多走一步，后者的代价是模型自信地答错。

**根因**

三层叠在一起，缺一层都不会这么糟：

1. **换行被抹平** → 模型失去"哪里是一条的边界"这个信息
2. **头+尾拼接没有说清** → 尾段被误认为紧接头部（假相邻）
3. **截断位置恰好落在答案之后** → 头里看不到，尾里只有一个"看起来像第一条"的

**修法**

1. 保留换行：按行 split → 行内多空格压成一个 → 丢空行 → 用换行 join。
   代码里用 `String.fromCharCode(10)` 而不是字面换行（见下一条教训）
2. 拼接必须自解释：标记写清「中间省略 N 字符，你看不到；**下一行直接是页面末尾，
   不是接着上面的**」
3. `MAX_TEXT_CHARS` 1200 → **3000**，并且轻微超限不截（1.25 倍容差）。
   page/2 的 3445 字符现在整段保留，47 行，`by Marilyn Monroe` 就在里面
4. 按行切要带容差：只在"退得不超过 30% 预算"时才切到行边界

**效果**

| 题 | 改前 | 改后 |
|---|---|---|
| R1 | ✅ 1 步 | ✅ 1 步 |
| R2 | ❌ 2 步答 Mark Twain | ✅ **2 步答 Marilyn Monroe** |
| R3 | ✅ 2~3 步 | ✅ 3 步 |
| R4 | ❌ loop | ❌ loop（与本条无关） |

**3/4 = 75%**，连跑两次完全一致（25% → 50% → 75%）。

**教训**

1. **`replace(/\s+/g, ' ')` 是"压缩文本"时最容易踩的地雷**。它抹掉的不是空白，
   是**结构**。要压也只压行内（`/[ \t]+/`），行之间有语义
2. 判断"截断有没有害"不能只看"丢了多少"，要看**丢掉的位置上有没有答案**。
   量一下关键字符串在全文里的下标，比读十遍日志有用
3. **头+尾拼接会制造假相邻**。凡是拼接，必须在接缝处明说"这里断了、下面是别处的内容"，
   否则模型会把它们当连续的上下文
4. 这次还有个纯工程教训：这段 JS 嵌在 Python 三引号字符串里，`'\n'` 要写两层反斜杠。
   我连续改错三次，每次都是 JS 语法错误。最后改用 `String.fromCharCode(10)` 彻底绕开。
   **当转义开始反复出错时，正确做法不是更小心，而是换一种不用转义的写法**

## 21. Web Component 的 shadow DOM 是感知盲区：搜索框明明在页面上，模型却说"这里不能输入"

**现象**

R4（在 MDN 搜索 Array.prototype.map 并读出返回值）从头到尾没进过门：

```
e2 是 button，不能往它里面输入文字（需要 input / textarea）
```

连续 6 步都在这个错上打转。听上去像模型选错了元素，但真实情况是：

**页面上压根没有它看得见的输入框。**

**定位过程**

1. 先纠正上一轮的错判。我之前写"元素上限 80 把搜索框挤掉了"，直接数一遍页面：

   ```
   document.querySelectorAll('input,textarea').length === 0
   ```

   **整个 light DOM 里一个输入框都没有**。所谓"搜索框被截断"根本不存在。
2. 那搜索是怎么做的？枚举所有自定义元素及其 shadowRoot：

   ```
   <mdn-search-button>  内部控件=1 可见=1  →  BUTTON title="Search the site"
   <mdn-homepage-search> 内部控件=1 可见=1  →  BUTTON text="Search"
   <mdn-search-modal>   内部控件=1 可见=0  →  <dialog><form><input type="search" placeholder="Search">
   ```

   **搜索入口和输入框全在 shadow DOM 里。** 我们的 `document.querySelectorAll`
   永远看不到它们 —— 模型的清单里从来没有"搜索"这个东西。
3. 关键验证：Playwright 的选择器能不能穿透 shadow DOM？
   造一个只有 shadow 内 button 的页面，给按钮打上我们的 `data-wp-id`：

   ```
   light DOM querySelector 找到: False
   Playwright locator 命中: 1
   点击: 成功
   ```

   **动作层没问题，只有感知层瞎。** 这条决定了修法：不用改动作，只改快照。
4. 补上 shadow 遍历后，问题变成第二个：弹窗开着时，模型去点被遮住的链接，
   Playwright 报 `<mdn-search-modal> intercepts pointer events`，重试 10 秒超时。
   也就是说弹窗外的东西**此刻真的点不到**，我们还在一股脑列给它。

**根因（两层）**

1. **感知层只走 light DOM**：`document.querySelectorAll` 到不了 shadow DOM，
   Web Component 里的控件对模型完全不存在
2. **弹窗遮挡没有被建模**：模态框打开时页面其余部分不可交互，但快照照旧全列，
   模型很自然地去点，然后卡在 Playwright 的重试循环里

**修法**

1. **快照遍历 open shadow root**（深度限 3）：
   - 元素收集、编号清理都改成遍历 `[document, ...各层 shadowRoot]`
   - 只穿 open：closed 的 shadowRoot 规范上读不到
2. **表单控件保底不截断**：94 个候选只列 80 个时，shadow 里的输入框排在最后正好被切掉。
   改成 `input/select/textarea` 优先占名额（上限的一半，至少 10 个），其余名额再按位置排
3. **放行 ARIA 文本框角色**：MDN 的输入框写的是 `<input type="search" role="combobox">`，
   而我们的 `type` 动作只允许 `input/textarea` —— 把 `combobox/searchbox/textbox` 一并放行
   （这条校验的本意是"别往按钮/链接里打字"，不是排斥 ARIA 角色）
4. **模态框聚焦**：弹窗打开时只列弹窗里的元素，并在快照里写明
   「当前有弹窗打开，外面点不到，弹窗里的输入框是唯一能输入的地方」

**效果**

| 阶段 | R4 |
|---|---|
| 修之前 | ❌ 6 步 loop，全程 `不能往 button 里输入` |
| 只加 shadow 遍历 | ❌ 6 步，弹窗开着去点被遮的链接 → 超时 |
| + 表单保底 + ARIA 角色 + 弹窗聚焦 | ✅ **success，6 步**，答出「返回一个新数组」 |

全量：**4/4 = 100%**（连跑两次一致）。从 25% → 50% → 75% → 100%。

**教训**

1. **"页面上明明有，模型就是看不到"要先怀疑感知层，不要先怀疑模型。**
   这次量化一下就清楚了：light DOM 里 `input` 数量 = 0，它当然找不到
2. **Web Component 是现代站点的常态**（MDN、企业后台、Chrome 自身 UI 都用）。
   只走 light DOM 的 Agent 在这类站点上等于半盲，这不是为一个评测题做的补丁
3. **弹窗不只是"多了一个元素"，而是"其余元素全部失效"**。
   不建模这件事，Agent 会一直去点被遮挡的东西，然后把时间耗在重试上
4. 又一次验证：**先取证再动手**。上一轮我凭"元素被截断"的猜测差点去做"按相关性排序"，
   而真正的原因是 shadow DOM —— 两件事的修法完全不同

## 22. 改成增量落库之后，最后一步永远丢：`finish` 忘了 flush

**现象**

M2 把"每步重写整个 trace.json"改成"每步只 INSERT 新增的行"。改完跑一个 2 步任务：

```
tasks.steps = 2        （任务表说走了 2 步）
task_steps            只有 1 行
runs/<id>/trace.json  2 行
```

**数据库比文件少一行**，而且少的是最关键的那一行 —— `finish`（也就是最终答案）。

**定位过程**

1. 先确认不是写入逻辑的问题：`trace.json` 里明明白白两行
   （`step 1 click e43`、`step 2 finish 'Marilyn Monroe'`）
2. 那就只剩"这两行为什么没都被推给落库回调"。落库是挂在 `on_step` 上的，
   而 `on_step` 由 workflow 的 `_flush()` 触发 —— 去看 `_flush()` 都在哪里被调用
3. 找到 `step_act` 里的 FINISH 分支：

   ```python
   if action.action is ActionType.FINISH:
       self.answer = action.answer or ""
       self._record(action, ok=True, error=None, started=started)
       return self._stop("success")      # ← 直接 return，下面的 flush 到不了
   ```

   同一函数末尾本来是有的：`await self._flush()`，但被这个提前 `return` 跳过了。

**根因**

**这是一个被 JSON 全量写掩盖了很久的 bug。**

以前每步都重写整份 trace，最后 `_run` 还会再 `files.save_trace()` 全量写一次 ——
所以哪怕最后一行从没经过 `on_step`，文件里照样是完整的。
换成增量落库后，"没被 flush 的行"就真的丢了。

换句话说：**M2 没有制造这个 bug，只是把它暴露了**。
这类"改了持久化策略才发现上游少发了一次通知"的情况，非常值得记一笔。

**修法（两层）**

1. 治根：FINISH 分支补上 `await self._flush()`
2. 兜底：`_run` 收尾时，拿 `result["trace"]` 和"已写行数"比一下，把差的补写进去。
   因为还有别的退出路径不走 `on_step` —— 超时、没预料到的异常，
   它们的行只存在于内存里。少了这层，DB 会长期比文件少几行。

**验证**

```
task_id                    DB  JSON
20261024-134519-q2q0h9      1     1  ✓
20261024-134525-ytk680      2     2  ✓
20261024-134537-6ngwa6      3     3  ✓
20261024-134559-v25wze      7     7  ✓
```

四题评测仍 4/4，未退化。

**教训**

1. **"增量写"会把"漏发一次通知"从无害变成丢数据**。改持久化策略时，
   要重新审视所有"发通知"的地方，尤其是提前 return 的分支
2. **两套持久化并存时，必须逐条对账**，不能只看"接口返回对了"。
   API 读 DB 成功、DB 少一行，表面完全看不出来
3. 时间字段也要对账：DB 存 TIMESTAMPTZ，取回来是 UTC；JSON 里是本地时间。
   不转时区的话，同一个任务两个来源差 8 小时，看起来像数据错乱

## 23. 以为在跑 chrome.exe，其实跑的是 chrome-headless-shell

**现象**

M3 做完共享浏览器之后想量一下内存，按 `imagename eq chrome.exe` 数进程：

```
计数: 0
```

**任务明明刚刚成功跑完**，浏览器进程却一个都没有。第一反应是"浏览器泄漏了 / 提前关了"。

**定位过程**

1. 换另一个进程工具再数一次 —— 有 5 个进程，但名字是 **`chrome-headless-shell`**
2. 也就是说：Playwright 在 `headless=True` 时启动的不是 `chrome.exe`，
   而是它另外带的 **headless shell**（一个裁掉 UI 的独立二进制）
3. 顺带纠正一个之前的说法：我一直以为跑的是
   `ms-playwright/chromium-1248/chrome-win64/chrome.exe`
   （`browser_type.executable_path` 返回的确实是这个路径），
   但**实际执行的二进制是 headless shell**。
   `executable_path` 说的是"这个 browser type 的完整版在哪"，不等于"这次启动的是哪一个"
4. 数出 0 还有第二个原因：沙箱里原生的 tasklist 看不到这些进程，换工具就能看到。
   所以那次"0 个"是**工具可见性问题叠加名字猜错**，两个坑撞一起了

**根因**

Playwright 新版本把 headless 模式改成了独立的 `chrome-headless-shell` 二进制
（更轻、启动更快），名字和 `chrome.exe` 完全不同。用旧名字去数永远是 0。

**测量结果（顺便把共享浏览器的收益量化了）**

3 个任务并发执行时：

```
进程数 = 5   总内存 ≈ 330MB
```

一个 Chromium 本身就带若干辅助进程（browser / gpu / network / renderer），
所以"5 个进程"是**一个浏览器**，不是五个。

对比 P1 的做法（每任务一个 Browser）：3 并发 ≈ 3 个浏览器 ≈ **1GB**。
共享 Browser + 每任务一个 Context 省掉约 2/3 内存，还省掉每任务 1~4s 的冷启动。

**教训**

1. **"进程数为 0"先怀疑名字猜错，再怀疑泄漏**。`executable_path` 返回的是类型路径，
   不等于实际启动的二进制
2. 这个发现对反爬侧有直接影响：`chrome-headless-shell` 的指纹比正常 Chrome 更明显
   （不用看 UA，二进制名本身就是特征）。以后要过检测，光换 `channel="chrome"` 不够，
   还得离开 headless —— 而那会牺牲"无界面"这个前提
3. **Windows 上不同工具看到的进程集合可能不一样**。同一个"数进程"的动作，
   换工具结果就从 0 变成 5

## 2026-10-26 · 改了已执行的迁移，downgrade 时删一个不存在的索引

**现象**

给 `0002_knowledge` 迁移补加 `content_hash` 列和 `knowledge_hash` 索引后，
执行 `alembic downgrade 0001_initial` 想重建表，报：

```text
DROP INDEX knowledge_hash] (Background on this error at: https://sqlalche.me/e/20/f405)
```

**定位过程**

1. 版本号还是 `0002_knowledge`，表还在、72 条数据没丢 —— 说明 downgrade 在事务里失败了并回滚（PostgreSQL 的 DDL 是事务性的，这点救了数据）
2. 想通关键：**数据库里的 0002 是按"旧版文件"执行的**（那时还没有 knowledge_hash 索引）；
   而 downgrade 跑的是"新版文件"里的降级代码（要删 knowledge_hash）→ 索引不存在 → 报错
3. `alembic upgrade head` 也不会救场：版本号已经是 0002，无事可做

**根因**

**迁移文件一旦在某个库上执行过，它的 upgrade/downgrade 就成了历史**。
修改它只对"从没执行过的库"生效；对已执行的库，新旧两版代码在同一个版本号下打架。

**修法**

本库只有本地一份、数据是回填产物可重建，所以直接手工重置：

```sql
DROP TABLE IF EXISTS knowledge_nodes;
UPDATE alembic_version SET version_num = '0001_initial';
```

再 `alembic upgrade head` 重建。**正确做法本该是新增 0003 迁移**（ADD COLUMN + CREATE INDEX），
不动 0002 —— 这次图快走了捷径，生产环境绝不可以。

**教训**

1. 迁移文件是"只追加"的账本，不是普通代码；要改结构就加新 revision
2. 已执行迁移被改过之后，`downgrade` 的行为是不可信的 —— 它会引用历史上不存在的对象
3. 走捷径前先确认两件事：**这个库的数据能不能重建**、**有没有别人依赖这个版本号**

## 2026-10-26 · 知识入库重复：72 条节点里只有 10 条是不同内容

**现象**

第一次回填成功（51 个任务 → 72 条节点），但检索试跑时 top-3 全是**同一条知识**：

```text
[查询] 无线鼠标多少钱
  task_answer sim=0.738 | 任务：在产品列表页找出所有价格低于 100 元的商品名称...
  task_answer sim=0.738 | 任务：在产品列表页找出所有价格低于 100 元的商品名称...
  task_answer sim=0.738 | 任务：在产品列表页找出所有价格低于 100 元的商品名称...
```

**定位过程**

1. 直接统计：`count(*)` = 72，`count(DISTINCT md5(content))` = 10 —— **重复率 86%**
2. 想来源：eval_real 的 4 道题被跑了十几轮，每轮都是一个独立 task_id；
   同样的 goal + 同样的 answer = 同样的 content，各存一份
3. 后果推演：检索 top-k 的 k 个名额被同一知识的多份副本占满，
   等价于 k=1 —— 检索功能名义上存在、实际上退化

**根因**

`flush_task` 只做了"按 task_id 幂等"（同任务重跑不重复），
没做"按内容去重"（不同任务采到同样内容仍会各存一份）。
幂等和去重是两件事：前者防重跑，后者防同源重复。

**修法**

1. `knowledge_nodes` 加 `content_hash`（sha256，64 hex）+ 普通索引
   —— 不直接用 content 建唯一索引：长文本 btree 索引有 2704 字节长度上限
2. `flush_task` 写入前按 hash 查重，已存在则跳过（保留最早入库那条，
   溯源指向"第一次采集到它的任务"，语义上也更对）
3. 顺序关键：**先删自己旧节点、再查重**——否则同一任务重跑会被自己的旧节点挡掉

结果：72 → 10 条（4 页面级 + 6 任务级），检索 top-3 恢复为三条不同知识。

**教训**

**评测反复跑同一批题，会把"数据重复"放大成"检索失效"**。
凡是"同一输入产生多份记录"的管道，入库层就必须有内容指纹去重；
只在检索层做去重是治标——库里还在膨胀，回填越多次越糟。

## 2026-10-26 · `/runs` 静态目录绕过认证：隔离锁了正门，旁路大开

**现象**

M4 补完后端认证后，验收线"用户 A 用 B 的 task_id → 404"是通过的，
却发现**任何人不带任何 token 都能读到别人的任务全文**：

```
GET /runs/20261025-102357-cw9p44/meta.json   → 200
{"goal": "这个页面上第一条名言是谁说的？", "answer": "Albert Einstein", ...}
```

**定位过程**

1. 逐条核对 M4 清单：`get_current_user` 挂了、`assert_owned` 逻辑对、
   `/stats` 有 user_id 过滤 —— 正门没问题
2. 换思路：不查"哪些接口做了校验"，改查"**同一份数据还有几条到达路径**"
3. `main.py` 里发现 `app.mount("/runs", StaticFiles(directory=RUNS_ROOT))` ——
   静态挂载是 ASGI 应用，**不经过任何 FastAPI 依赖**，`Depends` 在这里根本不执行
4. 再顺藤：P4 的 `POST /knowledge/ask` 会把 `sources[].task_id` 返回给所有登录用户，
   而 task_id 正是 `/runs/<task_id>/` 的目录名

于是链条闭合：`ask → 别人的 task_id → /runs/<id>/meta.json`，全程合法接口。

**根因**

两个原因叠在一起：

1. **历史包袱**：`/runs` 裸挂载是 P1 时代加的（那时没有用户概念，静态目录就是公开目录）。
   M4 加了归属校验，但没有人回头看"同一份数据还有没有别的出口"
2. **认知盲区**：把"接口"等同于"路由函数"——静态挂载不对应任何函数，
   在按接口清单核对时天然会被漏掉

安全上这叫**旁路（side channel）**：主通道锁得再严，只要有一条未上锁的路通向同一份数据，
隔离就等于没做。

**修法**

1. 删掉 `StaticFiles` 挂载，改成 `app/api/media.py` 里的普通路由：
   后缀白名单 → 路径穿越校验 → HMAC 验签 → `FileResponse`
2. 为什么用签名 URL 而不是 `Authorization` 头：截图是 `<img src>` 加载的，
   **浏览器发图片请求时不带自定义头**（浏览器行为，改不了）。凭证只能进 URL，
   即 S3/OSS 的预签名 URL 思路
3. meta.json / trace.json 加进"后缀黑名单"：**即使签名正确也 403**，
   任务全文只保留一条合法出口（带归属校验的 `/api/v1/tasks/{id}`）
4. `scripts/check_isolation.py` 把这条链路固化成 16 项断言，以后谁改动都能立刻发现倒退

**教训**

隔离做完后要做一遍"**换路径攻击**"：不是问"我该给哪些接口加校验"，
而是反过来问"**这份数据还能通过什么方式被读出来**"——静态目录、导出接口、
日志、缓存、`/docs` 里的示例、错误信息，都算。

## 2026-10-26 · 迁移加了新列，忘了回填历史数据

**现象**

`0003_knowledge_owner` 给 `knowledge_nodes` 加了 `user_id` 并成功 upgrade，
代码入库路径也写入了 owner，但库里 143 条历史节点的 `user_id` **全是 NULL**。

**定位过程**

1. 迁移日志显示 upgrade 成功，没有报错
2. 抽查新数据：新入库的节点有 user_id → 说明写入路径没问题
3. 查历史数据：`SELECT count(*) WHERE user_id IS NOT NULL` 得 0
4. 回看迁移文件：只有 `add_column` / `create_index` / `create_foreign_key`，
   **没有任何 UPDATE 语句** —— 新列默认值就是 NULL，历史行当然全是空

**根因**

把"加列"当成了"迁移的全部"。加列只是让结构就位，**已有行的数据迁移是另一件事**。

```python
op.execute("""
    UPDATE knowledge_nodes AS k
    SET user_id = t.user_id

    WHERE k.task_id = t.id AND k.user_id IS NULL
""")
```

3. 重新 upgrade，校验 143/143 全部有 owner

**迁移一旦在某个环境执行过就只能追加新迁移**（本次能改是因为只有本地跑过，

## 2026-10-26 · React setState 设成相同的值不触发重渲染，副作用不重跑

**现象**

"我的任务"列表里点**当前正在展示的那一条**，右列先被清空，
然后永远停在"还没有任务"，再点也没反应（点别的任务正常）。

**定位过程**

1. 点别的任务正常 → 说明加载逻辑本身没坏
2. 点同一条挂掉 → 差异只在"新旧 task_id 是否相同"
3. 看 `openOwnTask`：`setTaskId(id); setPollTaskId(id)`，
   而轮询 `useEffect` 的依赖是 `[pollTaskId]`
4. 关键：React 对 `setState` 用 `Object.is` 比较，**新值与旧值相同时直接跳过**，
   连 re-render 都不发生 → effect 不重跑
5. 但 `openOwnTask` 里已经先执行了 `setMeta(null); setTrace([])`（把视图清空），
   于是"数据清了、没人再去取" —— 死状态

**根因**

用"值"驱动副作用，而这个值**可能被设成同样的值**。此时"用户要求重新加载"这个意图
在 state 层丢失了：state 只能表达"当前是哪个任务"，表达不了"刚刚又点了一次"。

**修法**

加一个单调递增的 nonce 作为 effect 的额外依赖：

```tsx
const [pollNonce, setPollNonce] = useState(0);
// 每次"要求加载"就 +1
const openOwnTask = (id: string) => { ...; setPollNonce((n) => n + 1); };
useEffect(() => { ... }, [pollTaskId, pollNonce]);
```

**教训**

**凡是"事件"（要求刷新、要求重试、要求重新加载），不要指望用"状态值"去表达**——
值可能不变。要么用自增 nonce，要么直接把动作写进事件处理器里。
反之，"状态"（当前选中哪个任务）才适合用值表达。

## 2026-10-26 · 归属校验把"任务不存在"吞成空 dict，404 变成了 200 `{}`

**现象**

补审批接口时顺手试了一个随便编的 task_id：

```
GET /api/v1/tasks/20260101-000000-nosuch
→ 200  {}
```

**定位过程**

1. 接口里明明写着 `if meta is None: raise HTTPException(404)`，逻辑看着没问题
2. 那就只能是 `meta` 不是 None —— 断点打出 `assert_owned` 的返回值：`{}`
3. 回到 `assert_owned`：

```python
if meta is None or user is None:
    return meta or {}          # ← None or {} == {}
```

两个条件合并成一个分支，`None` 被 `or {}` 抹成了空字典，
调用方那句 `if meta is None` 永远为假，直接 `return {}` → 200。

**根因**

**把"任务不存在"和"没登录"当成同一件事处理**。前者是"这个 id 不存在"，
后者是"不校验归属"。它们要返回的东西根本不同：一个该报 404，一个该放行。
合并分支后，只能用一个返回值同时表达两种语义，于是必然有一边表达不出来。

**修法**

拆开，并且让"不存在"在这一层就地报 404，不推给调用方：

```python
if meta is None:
    raise HTTPException(404, "任务不存在")
if user is None:
    return meta
if meta.get("user_id") != user.id:
    raise HTTPException(404, "任务不存在")
```

**教训**

- **两个 `if` 条件用 `or` 合并，先问一句"它们该不该有同一套处理"**。
  合并省下两行，代价是语义被压平——这类 bug 单测很难覆盖到，因为没人会去测
  "不存在的任务"（测试都围绕真实存在的对象写）。
- "不存在 → 404"这种结论**尽量在自己这一层给死**，别用返回值把判断推给上层：
  上层的每个调用方都得记得判一次，忘一个就多一个 200。

**现象**

设计 P5a-2 的 `GET /tasks/{id}/approval` 时发现：任务批准完、续跑完、

**现象**

`snapshot_url` 最多能回答"回到哪一页"，回答不了"回到什么状态"。

  （表单值、勾选状态、选中项），恢复时先回填再执行。
- 验证方式：不要只看 `ok=True`。**动作成功 ≠ 做对了**。

  （这里是：提交的内容里得有姓名），否则绿灯毫无意义。

**现象**

续跑第一版：审批项显示 approved、trace 里也有一条 `click [e6]`，
状态一路往下走，但**界面毫无变化**，页面正文一个字都没多。

最迷惑的地方是它看起来像"审批没生效"，实际审批早就生效了。

1. 先确认动作真的被执行了：trace 有这一行 → 执行路径没断
2. 再看 error：`element detached` / 等待选择器超时 → 页面上根本没有那个元素
3. 回到 `selector_for`：`e6` 被翻译成 `[data-wp-id="e6"]`
4. 而 `data-wp-id` 是 `take_snapshot()` 里的 JS **现拍现打**的属性
   （`el.setAttribute(ATTR, id)`），页面本身没有这个属性
5. 续跑是**新开的浏览器**，`goto` 之后页面上一个标记都没有 →
   `[data-wp-id="e6"]` 选不到任何东西

**根因**

**把"快照里的临时编号"当成了"DOM 里的稳定标识"**。
`e6` 的含义是"这一轮快照里第 6 个可交互元素"，它的生命周期只有一次快照。
跨恢复用它定位，等于拿一张过期地图找路。

顺带说明为什么不能"每次 goto 后靠编号顺序对上"：编号是按
（是否在视口内, DOM 顺序）排序后重新编的，滚动位置一变顺序就变，
`e6` 可能指向完全另一个元素——**点错比点不到更糟**。

**修法**

续跑时按**语义身份**重新定位，而不是按编号：

1. 先拍一次快照（让新页面也带上标记）
2. 从暂停那一行的 `decision.snapshot` 里取出旧元素 → 拿到 `role` + `text`
3. 在新快照里找 `role` 与 `text` 都相同的元素 → 用它的新编号
4. 找不到 → **放弃执行**，把"页面已变，原动作没执行"作为提示交给模型

**教训**

- 任何"id"都要先问一句：**它是稳定的，还是这一轮生成的？**
  会话内的临时 id 不能跨越进程/浏览器生命周期使用。
- 需要跨生命周期定位时，用**语义键**（角色 + 文字）或**稳定路径**（XPath/CSS path），
  不用序号。序号最脆弱，因为它依赖"前面有多少个兄弟"这种会变的东西。
- 放弃执行比猜一个目标好：人批准的是"提交那个按钮"，不是"随便哪个按钮"。


4. 关键观察：目标每轮都完整重读一遍，notice 只有一句、而且在最后。

## 2026-10-26 · 拒绝之后模型换个步号再提同一个动作：审批乒乓没有出口

**现象**

修完上一条（理由进 `[用户否决]` 段）之后，主场景通了：拒 1 次 → 模型改成读按钮 → `success`。
但把拒绝次数上限放开到 4 次做压力测试时发现另一条路：

```
s4 [暂停] click 提交      → 拒绝（理由：不要提交）
s5 click 提交 → 又停       → 拒绝
s6 click 提交 → 又停       → 拒绝
s7 click 提交 → 又停       → 拒绝
s8 click 提交 → 又停       ← 永远停下去
```

每一步都是**新的一步**，所以 `_is_looping()`（要求连续 3 次相同动作）拦不住——
它判的是"已执行的动作"，而这些动作一次都没执行过。
结果就是无限审批：每次都问人同一个问题。

**定位过程**

1. 先看 `_is_looping()` 为什么没拦住：它在 `step_act` 里调用，而动作被 gate 拦下后
   直接 `StopEvent`，**永远走不到 `step_act`**。所以"重复"这件事必须在 gate 层判，
   不能等 act 层
2. 那用什么当"同一个动作"的身份？`describe(action)` 是 `click [e6]`——
   带编号。浏览器重开后编号会变（e6 → e5 → e12），拿编号当身份，
   同一个「提交」按钮会因为编号不同被当成不同动作。这正是上一个坑的同款错误。

**根因**

两道口子叠在一起：

1. **判重的位置错了**：重复检测放在"执行之后"（`step_act`），而审批拦截发生在"执行之前"，
   被拦下的动作永远走不到判重逻辑 —— 于是"永远不执行"就等于"永远不判重"。
2. **判重的身份用错了**：编号是当轮快照的临时属性，拿它当动作身份，
   换一个浏览器实例就认不出来。应该用元素文字（语义身份）。

**修法**

1. 动作黑名单 `self.rejected_actions: list[str]`，键 = `动作类型 + 元素文字`
   （`click:提交`），**不含编号**；元素文字从**暂停那一刻的快照**里查
   （`_decision_inputs["snapshot"]`）——因为被拒动作的 target 是老编号，
   当前快照里根本没有那个 id，只查当前快照会退化成 `click:e3`，黑名单形同虚设
2. 在 `step_gate` 里、调 `approval_gate` 之前判黑名单：命中就 `_stop("loop")`，
   理由写成"用户已经拒绝过「click [e6]」，模型仍坚持要执行同一个动作，已停止"
3. 黑名单随 `context.rejected_actions` 落库，跨 worker 进程/浏览器实例都有效；
   续跑时恢复

**教训**

- **判重的逻辑要放在"动作发生之前"还是"之后"，取决于你要防的是什么**。
  防"原地打转"放在执行后没问题（有轨迹可比）；防"反复问人"必须放在问人之前——
  因为被拦下的动作不会留下任何执行痕迹。
- 又一条"别拿编号当身份"。同一个错误在这个项目里出现了两次
  （`_relocate_target` 一次、这里一次），说明它是个**模式**而不是偶发失误：
  凡是跨生命周期的比较，先问"这个 key 会不会变"。
- 安全网要接受它的代价：黑名单让人"第二次改主意"没有机会了。
  这个代价明写在计划的风险表里——不加黑名单的代价是"人每分钟被打断一次"，更糟。

   `return`，所以那段出问题的代码只有"解密成功"才会执行到。范围一下就锁住了。
2. 看那个字段到底是什么类型：`repo._credential_dict()` 里写的是
   `"expires_at": _fmt(row.expires_at)` —— `_fmt` 返回 ISO 字符串。
   而我在 `_resolve_storage_state` 里写的是 `row["expires_at"].timestamp()`。
   同一个名字，两层含义：**DB 里是 datetime，出到服务层是字符串**。
3. 真正该问的不是"它是什么类型"，而是"我为什么在这里又算一遍"。
   `_credential_dict` 上面几行已经把 `expired` 布尔算好了（列表接口要显示
   "已过期"）。我在执行路径上重算一遍，等于把同一个判定写了两次。

**根因**

**在已有唯一实现的地方，旁边又写了一份。**
两处都在算"这份会话过期没有"，一处用 `datetime` 比、一处用 `timestamp()` 比。
只要两处的输入类型约定稍微不同（这里就是 datetime vs ISO 字符串），
晚写的那一份就会炸——而且是在"另一份明明是对的"的情况下炸，很容易误判成
"数据坏了"而不是"我写错了"。

这和 P5a 那次"白名单校验写两份，`_assert_allowed_url` 和 `session._assert_host`"
是同一类问题：**同一个判断有两个实现，早晚漂移**。

**修法**

不解析字符串、不 import `datetime`，直接用已经算好的那个布尔：

```python
note = ""
if row.get("expired"):          # ← repo 层算好的，不再自己比时间
    note = "这份登录态可能已过期，如果看到登录页请重新保存一次"
```

同时把这层契约写进测试：`test_resolve_warns_but_still_uses_expired` 的假数据
给的是 `{"expired": True}` 而不是一个过去的 `datetime`。于是"这里只认布尔"
变成了测试能守住的事实，而不是注释里的一句叮嘱。

**教训**

- 出现 `AttributeError: 'X' object has no attribute 'Y'` 时，除了问"它为什么不是 X"，
  更该问一句"**我为什么要在这里拆它**"。很多这类错误的答案是"我不该拆，别处已经给我了"。
- 判断"某处要不要重算"的标准：**这个判定在别处是否已经存在**。
  存在就传结果，不要传原材料——材料每转一层就可能换个形状。
- 同一个功能的两段代码结果不同（一段绿一段红）时，先找**分叉点**（哪一行之后行为不同），
  比读整段代码快得多。这次分叉点是"解密成功才往下走"，5 秒就定位到了。

## 2026-10-26 · 准备代码放在 try 外面：任务永久停在 running，且没留下任何痕迹

**现象**

修完上一条的 `AttributeError` 之前，第 6 段那个任务的表现是：

```
status:  running
steps:   0
note:    (空)
credential: (字段根本不存在)
```

前端一直转圈，等到 180 秒我的脚本自己超时。任务不是"失败了"，是**停在那里不动**，
而且数据库、meta.json、trace 里**没有任何一条线索说它遇到了什么**。

**定位过程**

1. 第一反应是"worker 卡住了"。但第 7 段的任务在同一个 worker 上 14 秒就跑完了
   —— 所以 worker 活着，是有东西把**那一个任务**卡住了。
2. 看 meta：`steps: 0`。这是一个非常有信息量的数字——说明 workflow **一步都没走**。
   而 `status: running` 是 `execute_task` 一进来就写的。所以卡点在
   "写了 running" 和 "workflow 开始跑" 之间。
3. 这个区间里 P5b 新加的只有一件事：`_resolve_storage_state()`。
   而它恰好**在我写的 `try:` 外面**。
4. 去翻 worker 的 stderr（不是任务日志，是进程日志），看到了真相：

```
0.06s ! run_task failed, AttributeError: 'str' object has no attribute 'timestamp'
```

异常一路冲出 `execute_task`、冲出 `run_task`，被 arq 捕获并记为 job 失败。
而 arq 的 job 失败**不会去改我们数据库里的任务状态**——它不知道那回事。

**根因**

**`try` 的边界画错了。**

我当时的理由是"这是执行前的准备，不是执行中出的错，让它冒到外层更好查"。
两个判断都错了：

1. "准备不会出错"是假的。准备工作一样会碰到数据形状、外部依赖、配置问题。
2. "冒到外层更好查"更假。`execute_task` 的 `except` 是**唯一**会写终态的地方
   （`status=error` + note）。让它冒出去，等于主动放弃写终态——
   于是最坏的情况出现了：**失败但看起来像还在跑**。

这比"报错"糟得多。报错用户至少知道"这条路走不通"；永远 running
用户只会一直等，而且事后没有任何东西可查。

**修法**

把 `_resolve_storage_state` 整段搬进 `try:` 里面（和 `BrowserSession`、
`workflow.run` 并列）。这样任何异常都会走到那个 `except Exception`，
任务以一个**看得见的** `error` 收尾，note 里带上异常类型。

残留问题：arq 的 job 失败仍然没人写终态。
当时唯一的兜底是进程重启时的 `mark_interrupted()`——实测有效
（重启 worker 后那个僵尸任务确实从 `running` 变成了 `interrupted`），
但它要求"进程重启"这个不一定发生的条件。
**这条残留已在下一条解决**（job 层兜底）。

**教训**

- **`try` 的边界该按"失败了会不会有人写终态"来画，不是按"这是准备还是正活"来画。**
  只要一段代码失败后会导致"状态永远停在中间态"，它就必须被能写终态的那层包住。
- "看起来还在跑"是比"明确失败"更差的用户体验，也是更差的工程状态：
  它对用户是无限等待，对开发者是零信息量。
- 排查"卡住"类问题的顺序：先看 `steps`（区分"没开始"和"跑到一半"），
  再看**进程日志**而不是任务日志——任务日志是任务自己写的，
  而"任务自己都没来得及写日志"恰恰是这类 bug 的特征。

## 2026-10-26 · 兜底捕获异常之后要不要重新抛？这道题没有"都对"的答案

**背景**

上一条（异常冲出 `try` → 任务永久 running）的源头修完就够了吗？不够。
源头修的是"P5b 那段代码不该在 try 外面"，而**没有任何机制保证下一个人不犯同样的错**。
所以还要一道 job 层的兜底：`worker.run_task` / `resume_task` 各包一层 try，
捕获后写终态。

写的时候卡在一个具体问题上：**捕获之后，还要不要 `raise`？**

**两个方向都"有道理"，但后果完全不同**

| 选择 | 好处 | 代价 |
|---|---|---|
| `raise` 出去 | arq 会记录 job failed，监控/日志里有痕迹 | arq 可能**重试这个 job** |
| 吞掉不抛 | 绝不会重复执行 | arq 那边看起来"成功了"，得自己记日志 |

关键在于：**这个项目的任务执行有副作用**。
「提交」按钮被点第二次、表单被填第二遍、订单被下两单——
这些后果比"状态不准"严重得多，而且不可撤销。

所以选**吞掉**。arq 的重试语义是为幂等任务设计的（发通知、刷缓存），
而我们这个 job 一点都不幂等。

**但"吞掉"必须配一件事，否则更糟**

只吞不写终态 = 静默失败。任务永久 running、没有任何错误痕迹——
这正是上一条描述的那个最难查的状态。所以：

> **吞异常和写终态必须成对出现。少任何一个，都比不捕获更糟。**

**第三层：兜底自己会不会失败？**

会。`mark_crashed` 里要写 meta.json（磁盘）和 DB。如果两个都挂了，
它自己就会抛。这时候如果让它抛出去：

```
原始异常 A（真正的原因）→ 兜底失败抛异常 B → worker 的 except 只看到 B
```

排查难度从"一个 bug"变成"两个 bug，而且你还不知道第一个是什么"。
所以 `mark_crashed` 内部再包一层 try，失败只 `log.exception`，**绝不再抛**。

这就是"兜底要兜到自己"——一个会抛异常的兜底不算兜底。

**验证方式（这次没只靠单测）**

5 条单元测试里 `mark_crashed` 是 mock 的，验的是"run_task 会不会调它、会不会重新抛"。
但"它到底写没写进 PostgreSQL"没人验——而这恰恰是它的全部价值。所以另做了一次真库实测：

```
造一条真任务（DB 行 + meta.json，status=running）
→ 把 execute_task 临时换成一个必崩函数
→ 调真实的 worker.run_task(ctx, ...)
→ 查两边状态
```

结果：

```
run_task 返回值: 20261026-190818-vabdig   （等于 task_id → 没重新抛 ✓）
meta.json status: error
meta.json note  : 执行进程内部错误（RuntimeError: 故意制造的内部错误…）
DB status       : error
DB note         : 同上
```

**教训**

- **"捕获后要不要抛"取决于这个动作能不能重做**。幂等就抛（让框架记一笔），
  有副作用就绝不能抛（重试等于把副作用做第二遍）。
- **兜底要成对**：吞异常 + 写终态。只做一半，一半的收益、两倍的害处。
- **兜底自己也会失败**，所以兜底里不能再抛——否则它会掩盖真正的原因。
  这个结构在哪儿都成立（清理函数、finally 块、错误上报）。
- 单测验"调了没调"很容易，验"真写进去了没"很难但更重要。
  **凡是"证据要留痕"的功能，都该有一次真库/真文件系统的验证**，
  哪怕只是跑一次就删的一次性脚本。

  trace 一落盘同时流去 trace.json / 实时 prompt / 回放器三处，

- `glm-4v-flash`：几乎不撞 429（偶尔一次，15s 内恢复）。

## 2026-10-28 · trace 加了字段，接口却看不到：JSON 的兼容性不适用于固定列的表

**现象**

P6a 的端到端脚本（check_vision.py）第一跑：任务成功、答案「5月 4700」完全正确，
`runs/<task_id>/trace.json` 里 `vision.used=true`、`trigger=task`、`ms=8304` 一应俱全，
可是脚本断言「trace 有 vision.used=true」红了——它查的是
`GET /api/v1/tasks/{id}/trace`，接口返回的行里**根本没有 vision 这个键**。
第二跑修好 vision 之后，又轮到「notice 含『视觉参考』」红：`decision` 字段同样不见。

**定位**

P6 计划第四节的原话是"trace 行新增 vision 字段，回放器/M5 前端忽略未知字段——
P5a 已验证过这种兼容性"。这句话被照着做了，但漏了一个前提：
**trace 有两个落点，一个能自动兼容，一个不能。**

- `runs/<id>/trace.json`：整个 dict 序列化，只增字段天然兼容；
- `task_steps` 表：**固定列**（`step_no / url / thought / action / ok / error /
  duration_ms / elements_total / screenshot / tokens`），
  `repo.insert_steps` 只按列名挑字段写，`fetch_steps` 只按列名拼 dict 返回。
  多出来的键在写入时**被静默丢弃**，读取时自然也没有——不报错、不打日志。

**根因**

把"JSON 的向前兼容"误当成了"存储层的向前兼容"。两者不是一个东西：
JSON 是开放式结构，DB 表是封闭式契约。
同一份数据存两处时，**字段要登记两遍**，少一遍不会报错，只会让一部分读者看不到。

**修法**

1. `tasks_steps` 加 `vision` 列（JSONB，nullable）——迁移
   `alembic/versions/0006_vision.py`，`models.TaskStep` 加字段，
   `repo.insert_steps` / `fetch_steps` 各加一行映射；
2. `decision` **不加列**：它是几十 KB 的完整决策上下文（含整份快照），
   进表等于让 `task_steps` 变成 blob 仓库——它**刻意只留在 trace.json**。
   所以验收脚本的这一项改成直接读磁盘上那份真相，并在注释里写明
   "这一项和 vision 是两类问题：一个是该加列没加，一个是刻意不入库"。

**连带教训**

- **验收脚本必须知道每个断言该读哪个源**：`vision` 读 API（顺便证明 DB 那条路通了），
  `decision` 读 JSON。写脚本时先问一句"这个字段存哪"，比红了之后猜半小时快；
- 断言红的时候先怀疑"我读的源对不对"，再怀疑"功能有没有跑"——
  这两次的答案都是"功能好得很，是读数的人站错了地方"。

## 2026-10-28 · 提示词替系统下了它没资格下的结论："这个动作无效"

**现象**

D1 扩题后跑 T8（"在商品搜索页搜索 zzz，告诉我一共有几条结果"）：模型先 `type e1 <- 'zzz'`，
然后 `click e3` 连点三次，判 loop，任务失败且没有答案。

**定位**

逐轮打 notice 才看明白：

- s2 的 notice 是"页面已更新，新出现的内容：『zzz value='zzz'』"（输入生效）
- s3、s4 的 notice 都是"上一轮动作执行后页面没有任何变化，**说明这个动作无效**；
  请换一个动作，或者如果信息已经够了就直接 finish"

而 s2 之后的快照是这样：

```
[正文] 商品搜索 返回首页 搜索 共 0 条结果
```

搜索**确实执行了**，结果就是 0 条 —— 页面当然不变。

**根因**

`step_observe` 只观察到"快照文本没变"，却升级成了"动作无效"这个**因果结论**。
两者不等价：搜一个不存在的关键词时，"无变化"恰恰是正确结果。
模型接到"动作无效"的暗示，推理只能是"那是没点上，我再点一次"，
于是连点三次撞上 loop 检测。

**修法**

只报事实 + 给两条出路，不下结论：

```
页面内容没有变化。可能是动作没生效，也可能是它生效了、但这页面的正常反应就是不改变显示
（比如搜索结果是空的）。当前页面信息够回答任务就直接 finish，否则换个动作，别重复刚才那个。
```

改前 T8 **1 次跑 → fail(loop)**；改后 **3/3 pass**，答"0"。

**连带教训**

提示词里每一句"这说明……"都是一次归因，而观察层只掌握现象。
**系统能说的只有它真看到的东西**，把"说明"留给模型自己下 —— 它下错了还能纠，
系统把它带偏了，它连纠的机会都没有。

## 2026-10-28 · 报错只说"类型不对"、不说"该写什么样"：模型只能重犯

**现象**

T6（只在姓名填李四、其余留空提交，然后读回显）连续 3 轮 `invalid_action`，
1 步就结束，答案为空。原始输出是：

```json
{"thought": "在姓名输入框中填写李四", "plan": ["填写姓名","提交表单"],
 "action": {"action": "type", "target": "e1", "text": "李四"}}
```

action 被套成了一个对象。

**定位**

`parse_raw` 抛的文案是 `动作格式不对：Input should be a valid string` ——
这是 Pydantic 的英文原文，写给人看的。模型看到它之后，第二次输出是：

```json
{"thought": "输入姓名李四", "action": {"type": "type", "target": "e1", "text": "李四"}}
```

它把 key 从 `action` 改成了 `type`，**越改越远**。两次非法 → invalid_action。

**根因**

纠错提示只说明了"什么错了"，没有说明"该写成什么"。
对开发者来说"类型错了"足够定位；对模型来说，它需要在**一次**重试里改对，
否则第二次就要收尾。所以报错必须自带可照抄的样例。

第二版修法还踩了一个小坑：第一版文案里写了"target/text/option 才是它的参数"，
模型于是造出 `{"type":"type",...}` —— **给它术语，它会拿术语拼新东西；给它样例，它才会抄。**

**修法**

报错直接摆样例：

```
动作格式不对：action 的类型错了（Input should be a valid string）。
正确形状例如 {"thought":"一句话","action":"type","target":"e1","text":"李四"}：
action 只填字符串（goto/click/type/select/scroll/finish），target/text/option 才是它的参数，
不要把 action 写成对象。
```

并补一条单测 `test_parse_raw_error_shows_correct_shape` 锁住"报错里必须含可照抄形状"。

**连带教训**

所有"喂回给模型"的报错都是一个**提示词**，不是日志。
判据：**一个从没见过这个系统的人，能不能只按这句话改对？** 不能，就还得改。

## 2026-10-28 · Windows 上原子写会撞上"有人正在读"：整条任务被判 error

**现象**

D1 正式跑，T3 第 3 轮 `status=error`、0 步、空答案。
第一版评测报告把它归到"答案错误"，差点当成模型能力问题写进交付报告。

**定位**

`runs/<task_id>/meta.json` 里躺着：

```
note = "执行进程内部错误（PermissionError: [WinError 5] 拒绝访问。:
        'runs\\<id>\\meta.json.tmp' -> 'runs\\<id>\\meta.json'）"
```

**根因**

落盘用"写 .tmp 再 rename"保证原子性（`storage/files.py::_write_json`）。
**Windows 上只要目标文件被别的进程打开着，rename 就会失败**（目标不是文件句柄共享的）。
本项目的形态正好踩满：API 进程每秒轮询读 `meta.json`，worker 同时每秒重写它，
两边对上就是一发。

POSIX 上 rename 不受"有人正在读"影响（读者手里的 fd 仍指向旧 inode），
所以这个 bug **在 Linux 容器里跑一万次也复现不了**，只在本地 Windows 出现。

**修法**

对 `replace` 重试 6 次，间隔 10/20/30/40/50/60ms（最坏等 210ms，够躲过那一瞬，
又不至于让"磁盘满/只读"这类真失败拖住任务几秒）；失败到底则清理 .tmp 后如实抛出。

**没有选"加锁"**：写方只有一个（worker），冲突是瞬时的，加锁会把瞬时竞争变成排队，
而且会让 API 的读也被卷进来。重试是这类"瞬时占用"的正确解法。

补两条单测：第一次 replace 抛 `PermissionError` 后必须成功（且不留 .tmp）；
一直失败则如实抛出并清理 .tmp。

**连带教训**

评测脚本必须记 `meta.note`，并且**把"判定原因"和"后端说明"并排放在报告里**。
否则一条环境错误会被统计成"答案错误"，报告就成了假账 ——
这次差一点，是 `note` 里那行中文把真相救回来的。

## 2026-10-28 · 元换分写成 ×1000：报告里所有成本大了 10 倍，而它读起来毫无异常

**现象**

D2 成本脚本第一版跑出来，每任务成本显示「0.471 分」。
按 4711 token × 0.1 元/百万 = 0.000471 元手算验一下：**0.000471 元 = 0.0471 分**，
表格里却写着 0.471 —— 大了正好 10 倍。

**定位**

```python
if amount < 0.01:
    return f"{amount * 1000:.3f} 分"
```

1 分 = 0.01 元，元换分应该是 **×100**。×1000 是"毫"的量级（1 元 = 1000 毫）。

**根因**

换单位时凭"小数点移三位"的直觉写了系数，没有回到定义（1 分 = 0.01 元）验一遍。
更麻烦的是这类错误**不会自己暴露**：没有异常、没有负数、数量级也"看着像钱"，
报告读起来完全正常。同一份报告里另一处"1 元钱能跑 2122 个任务"其实是对的
（它走的是元口径），于是两个数字互相矛盾也看不出来 —— 一个错数和一个对数并排，
只会让人觉得"大概就是这么便宜吧"。

**修法**

1. 系数改成 ×100，并在函数 docstring 里写下"第一版写成 ×1000"这个事实，
   防止下次又凭直觉改回去；
2. 补单测 `test_yuan_to_fen_is_times_100_not_1000`（0.000471 → "0.047 分"），
   以及量级切换、档位顺序的断言 —— 这类"静默错数"只能靠测试兜；
3. 顺手把"1 元能跑多少任务"和"每任务成本"两个数放在同一段里**互相验算**，
   让矛盾能被眼睛抓到。

**连带教训**

**报告类代码的正确性风险比服务代码更高**：服务代码错了会报错、会被日志抓到，
报告代码错了只会安静地印出一个像模像样的数字，然后被人引用进 README、文档、PPT。
所以凡是"算给人看的数"，都要有一条能手算验算的锚点。

## 2026-10-28 · 构建神秘失败 exit 1073807364：先怀疑 Docker Desktop 本身，再怀疑自己的配置

**现象**

`docker compose build` 跑了 4 分 49 秒后异常退出，exit code 1073807364（十六进制
0x40010004，DBG_TERMINATE_PROCESS），**没有任何构建日志输出**（因为输出被管道
`| tail -60` 缓冲，进程死掉时缓冲区一起没了）。第一反应是怀疑 Dockerfile 写错了。

**定位**

重跑一次，把日志落盘到文件（`> build.log 2>&1`）而不是管道。这次立刻看到：

```
failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine;
The system cannot find the file specified.
```

守护进程的命名管道不存在 = Docker Desktop 整个没了。`tasklist` 一查，进程列表里
一个 docker 都没有——上一次构建跑到一半时 Desktop 崩了/被关了，把构建进程一起带走。

**根因**

两个独立的问题叠在一起：

1. Docker Desktop 在构建中途死掉（Windows 上偶发，资源紧张时更常见）；
2. 构建输出走了 `| tail` 管道——**长任务 + 管道缓冲 = 失败时什么都看不到**。

**修法**

1. 重启 Docker Desktop（引擎 server 版本能打印出来才算好：`docker version --format '{{.Server.Version}}'`）；
2. 长构建一律日志落盘：`docker compose build --progress=plain > log 2>&1`，失败时 tail 文件；
3. 排查顺序固化：**构建/运行"神秘失败"且无输出时，第一步查 daemon 活着没
   （`docker version` 能否返回 server），再查自己的配置**——配置错了至少会有报错，
   daemon 没了连报错都没有。

**附带的好消息**

Desktop 重启后重跑构建，**90 秒完成且全层 CACHED**——包括 15 分钟的浏览器层。
BuildKit 的层缓存存在 Docker 的数据目录里，daemon 重启不丢。所以"Desktop 崩了"
的代价只是时间，不是缓存作废，不必恐慌性改 Dockerfile。

**修法**

1. 首帧改成 `{"type": "session.start", "token": ...}`，并在脚本注释里写明
   协议定义在 `voice_ws.py:121`，下次改协议时能顺着找过来；
2. 判定逻辑里补一条经验：**"收到应用层错误"本身就是握手成功的证据**，
   排查时先分清失败发生在哪一层（网络 → HTTP 升级 → 应用协议），别被
   error 消息的字面意思牵着走。

**连带教训**

写协议双端的场景，**客户端测试代码的每一帧都要从服务端源码里复制**，不要默写。
协议是服务端定义的，测试是验证服务端行为的，用默写版去测等于自己跟自己对答案。


## 2026-10-28 · 容器里跑 check_*「半通」：API 调用全通，Chromium 却 nav_failed

**现象**

D5 要求"check_* 在容器环境里再跑一遍"。第一次跑 `check_redact`，8 项失败，
矛盾点在于：**脚本调 API 全部成功**（登录、提交任务、查审批都通），
但任务落到 `nav_failed`：

```
Error: Page.goto: net::ERR_CONNECTION_REFUSED at
http://127.0.0.1:8000/testsite/login.html
```

同一条 127.0.0.1:8000，前端调用通、浏览器导航拒——"半通"是最迷惑的失败形态，
因为你会本能地怀疑网络/白名单，而不是地址本身。

**定位**

顺着两条链分别看：

1. 脚本调 API：脚本跑在 **api 容器内部**（`docker compose exec api ...`），
   容器里 127.0.0.1:8000 就是 uvicorn 自己 → 通；
2. 浏览器导航：`start_url` 传给的是 **worker 容器**，由那里的 Chromium 去 goto。
   worker 的 127.0.0.1 是它自己，8000 端口上没有服务 → 拒。

（中途还踩了两个纯工具坑，一并记下：`docker compose run api` 起的是**只跑脚本的
新容器**，里面没有 uvicorn，所以那样跑必然连不上，得 `exec` 进正在跑的那个；
Git Bash 会把 `/app/scripts/xxx.py` 改写成 `D:/.../app/scripts/xxx.py`，
要加 `MSYS_NO_PATHCONV=1`。）

**根因**

一个变量承担了两种语义：`BASE` 既是"脚本调 API 的地址"，又被拿来拼"浏览器要访问的地址"。
宿主机部署时两者相同，容器里必须不同（服务名 vs 自己）。

**修法**

1. 六个 `check_*` 脚本的 `BASE` 改成 `os.environ.get("WEBPILOT_BASE", "http://127.0.0.1:8000")`；
   容器里跑时传 `-e WEBPILOT_BASE=http://api:8000`，两种用途一起走服务名；
2. `voice_ws._start_url()` 硬编码的 127.0.0.1 改成读 `settings.default_start_url`
   （新增配置项，compose 里注入 `http://api:8000/testsite/index.html`）；
3. `scripts/` 打进镜像（`COPY scripts/ /app/scripts/`），这样 `exec` 进去就能跑，
   不用每次 `docker cp`；
4. `check_credentials` 里那条断言也顺手修了——它把期望值写死成 `"127.0.0.1"`，
   换成 `urlparse(BASE).hostname` 后才对环境无关（见下一条）。

**连带教训**

**"容器里跑"不是把同一份脚本搬进容器就行**：脚本里每一个 URL 都要问一句
"这个地址最终是谁去访问的"——api 自己、worker 里的浏览器、还是宿主机的用户。
地址的**消费者**不同，正确的值就不同。

## 2026-10-28 · 加了一个配置字段，引发 10 分钟静默挂死（附一次误诊全过程）

**现象**

D5 收尾跑全量 pytest，卡在 73% 十分钟不动，只能强杀；逐文件二分后发现
是 `test_voice_ws.py` 的第 4 个用例（`test_full_round_event_sequence`）挂住。
而同一套测试在 D1/D2 阶段是 **292 passed / 0 skip**——中间我只加了一个配置项。

**定位（含一次误诊，如实记）**

1. 先排视觉开关：`VISION_ENABLED=false` 重跑，照样挂 → 不是它；
2. 再怀疑环境：`netstat -ano | grep -E ":(6379|5433|5432) "` 发现 5433 没监听
   （宿主机时代的 Postgres，容器化后停了）→ 判断"测试在等一个不存在的服务"，
   于是把测试搬进容器跑——**照样挂**，假设被推翻；
3. 上 faulthandler 抓栈（pytest 9 已经不支持 `--faulthandler-timeout`，改用手动注册）：

```bash
PYTHONFAULTHANDLER=1 python -m pytest tests/test_voice_ws.py -k full_round -q &
sleep 25; kill -ABRT $!
```

栈落在 `test_voice_ws.py:141 → msg = ws.receive_json()`，说明**服务端少发了一条消息**；
4. 临时在接收循环里打印每条消息，真相一句话：

```
{'type': 'error', 'code': 'submit_failed',
 'message': "任务提交失败：AttributeError: 'types.SimpleNamespace' object has no attribute 'default_start_url'"}
```

**根因（两层，缺一不可）**

1. `tests/test_voice_ws.py` 用 `SimpleNamespace` 造了个**假 settings**，只含 WS 端点
   用到的 6 个字段。我给 `config.Settings` 新增 `default_start_url` 后，
   `voice_ws._start_url()` 一读就 AttributeError —— 假对象不会跟着真类走；
2. 这个异常被 WS 端点包成 `error` 事件发回，但**测试的接收循环只认 `tts.end`**，
   于是 `receive_json()` 永远等下一条消息 → 表现成"挂死"，而不是"失败"。

**修法**

1. 假 settings 补 `default_start_url=""`，并在 docstring 里写下这个坑：
   **给 settings 加字段时必须同步改所有假 settings**；
2. 测试里把 `error` 当成终止条件：`assert msg["type"] != "error", msg` ——
   让将来的同类问题**立刻失败**而不是挂 10 分钟；
3. 部署形态变了就换地方跑测试：`docker compose exec api python -m pytest -q`
   （容器里 `DATABASE_URL`/`REDIS_URL` 指向 pg/redis 服务名，测试环境与运行时一致）。

**连带教训（三条，都很贵）**

1. **失败形态决定排查入口**：报错指向代码，"长时间无输出"指向"在等什么"。
   我一开始按第二条去查端口，方向对但对象错——真正在等的是**一条永远不会来的 WS 消息**；
2. **测试里的假对象是"影子配置"，加字段必炸**：凡是用 SimpleNamespace/mock 造配置的地方，
   都应该在注释里写明"加字段要同步这里"；
3. **超时是测试的基础设施，不是奢侈品**：一个接收循环没有超时，就把"断言失败"
   降级成了"CI 卡死"——后者要花十倍时间排查。
