## 三、方法论发现：这个系统是确定性的，1 轮就够

一开始我以为"8 个样本太少，25% vs 12.5% 分不清是修复效果还是噪声"，准备加样本量。  
加完之后发现两件事：

1. **同一题每轮走到同一个结局，连每步的可交互元素数都一样**
   | 题  | 三轮的每步元素数                                              |
   | -- | ----------------------------------------------------- |
   | R2 | `[55, 64, 40, 47, 44, 46, 43, 58, 49, 44, 49, 44]` ×3 |
   | R3 | `[55, 57, 29]` ×3                                     |
   | R4 | `[83, 98, 98, 94, 555, 520, 520]` ×3                  |
2. 原因在 `app/agent/llm.py:75`：`temperature=0.0`。  
   同一份快照 + 同一个 goal → 同一个动作序列。

**所以之前那次 12.5% 不是"统计噪声"，是一个具体的、可命名的基础设施 bug**（httpx2 竞态，  
见踩坑日志 #17）污染了样本。把噪声当成统计波动去加样本，方向就错了。

**实践结论**：

- 之后每次改动，**跑 1 轮 4 个样本就足以判断有没有变化**，迭代成本从 ~5 分钟降到 ~1.5 分钟
- 只有当改动**引入随机性**（换模型、加 temperature、加多路径重试）时，才需要多轮
- 留 3 轮的价值不在统计，在**证伪**：一旦某轮数字和其它轮不一样，说明引入了不确定性，  
  那件事本身就是要查的 bug

## 四、三道失败题的真根因（逐条带证据）

### R2 · 翻页：把"动作"当成了"任务"

**轨迹**（12 步，全部 `thought` 为空，`completion_tokens` = 15）：

```
s1  click → /page/2/   ...  s9  click → /page/10/
s10 click → /page/9/   s11 click → /page/10/   → loop 判定触发
```

**证据**：R1/R3/R4 的 `thought` 都正常，只有 R2 从第 1 步起就是空串。  
四道题首屏是同一个页面、同一份快照，唯一变量是 goal 文本  
（"点击下一页，告诉我新一页上第一条名言是谁说的"）。

**根因**：goal 里有一个祈使动作（"点击下一页"），模型把它当成了任务本身，  
只输出 `{"action":"click","target":"e62"}`（15 tokens，连 thought 字段都省了）。  
它**没有"我做完了"这个概念**，于是一路点下去，直到第 10 页没有 Next、点到了  
Previous 往回走，才被"连续相同动作"检测拦下。

**这类失败的正确修法不是换提示词措辞，而是给系统一个显式的"完成条件"**——  
见第五节。

### R3 · 标签导航：读到了，却不相信自己读到了

**轨迹**（3 步）：

```
s1 click e31  thought=需要点击标签 love 来查看其下的名言
s2 click e55  thought=找到标签 love 下的第一条名言，需要点击 'Next →' 来查看下一页
s3 finish       answer=C.S. Lewis
```

**curl 交叉验证**（标准答案不是猜的）：

| 页面                  | 第一条名言的作者                 |
| ------------------- | ------------------------ |
| `/tag/love/`        | **André Gide** ← 标准答案    |
| `/tag/love/page/2/` | **C.S. Lewis** ← 它给出的错答案 |

**根因**：第 2 步它已经站在 `/tag/love/` 上、André Gide 就在正文里，  
但它写下的 thought 是"需要点 Next 查看下一页"——**多点了一步**，  
于是在 page/2 上读到了"第二条名言"当答案。不是读不到，是不敢停。

> 附带说明：P1（白页兜底）在这题上是**真的生效了**。修复前这一步的快照是 `els=0`  
> （空白页，模型直接崩），修复后是 `els=29`（能继续走，只是走错了方向）。  
> 失败形态从"崩溃"变成"逻辑错"——**可诊断性提升了，但分数没变**。  
> 这正是"可观测性修复不涨分"的典型样本。

### R4 · 前端渲染 + 搜索：动作类型选错，然后在链接堆里打转

**轨迹**（7 步）：

```
s1 click e3    thought=搜索框在页面的上方，先点击搜索框
s2 scroll down thought=搜索框中没有找到 Array.prototype.map，需要滚动页面查找
s3 click e19   thought=... 先点击 JavaScript 链接
s4 click e9    thought=... 先点击 Functions 链接
s5-s7 click e19 ×3  → loop
```

**每步元素数**：`[83, 98, 98, 94, 555, 520, 520]`

**根因有两层**：

1. **动作类型选错**：搜索框应该是 `type`，它选了 `click`。  
   点完什么也没发生，第 2 步它把"没输入关键字"误判成"当前页面没有我要找的东西"，  
   于是开始滚动、然后点链接跑偏
2. **元素上限失效**：第 5 步起元素数暴涨到 555 / 520，而快照只保留前 80 个。  
   目标元素（搜索框、搜索结果）根本不在前 80 里 —— 模型看到的是一个  
   "看起来完整、实际被截断"的页面，越点越错

**这一题暴露的是渲染层设计问题**（截断策略），不是提示词问题。

## 五、三道题的共同点，以及它意味着什么

R2「不知道什么时候该停」、R3「读到了却不敢停」、R4「走错路还没纠错」——

**三个症状指向同一个缺失：系统里没有"任务进度"这个状态。**

当前每一步的输入是「goal + 当前快照 + 原始动作流水（history）」。  
模型每次都在重新读一遍 goal、重新看一遍页面，判断"现在该干什么"，  
但它**看不到"我已经完成了哪些子目标"**。

- R2 看不到"下一页已经翻过了"
- R3 看不到"第一条已经读到了"
- R4 看不到"我点的是一个搜索框，应该输入而不是点"

history 里虽然有动作记录，但那是**原始流水**（`click e43` / `scroll down`），  
不是**结构化进度**。对弱模型来说，"从流水里重建进度"这件事本身就没做。

**这不是加几句话能解决的，需要改数据结构**（每步让模型输出并维护一个  
`progress` / `done_criteria` 字段，下一轮回喂）。这也解释了为什么 P0~P2 一点分都没涨：  
它们动的是输入的表面积，不是决策的结构。

## 七、A 实施记录（任务分解 plan / progress）

### 7.1 动手前发现：管道已经存在，只是没接水源

`plan` / `progress` 这套东西**代码里早就写好了**：

- `workflow.py:179-180` 有 `self.plan` / `self.progress`
- `workflow.py:428` 有 `_absorb_plan()` 负责吸收
- `prompts.py` 有渲染 `[任务分解]` + `（已完成）/（未完成）` 的逻辑
- `workflow.py:276-277` 也传给了 `build_user_prompt`

但 `SYSTEM_PROMPT` 从头到尾**没让模型输出过 `plan` / `progress`**。  
于是 `_absorb_plan` 永远收到空 → `self.plan` 永远是 `[]` → `if plan:` 永远为假。

一条铺好但没接水的管道。所以这不是"新建数据结构"，是"把断掉的那截接上"。

### 7.2 迭代过程（两轮，第一轮掉分）

**第一轮**：提示词里加「多步任务第 1 步给 plan，之后用 progress 报已完成」，  
渲染里加一句「还剩 N 条未完成；全部完成后立刻 finish」。

结果 **1/4**，而且——

| 题  | 结果                       | 变化                      |
| -- | ------------------------ | ----------------------- |
| R1 | ❌ loop 6 步               | **从 1 步答对退化成 6 步打转**    |
| R2 | ❌ 答 Pablo Neruda（page/3） | 从 12 步 loop 变成 3 步、多翻一页 |
| R3 | ✅ 3 步 André Gide         | 从 0/3 变成通过              |
| R4 | ❌ invalid_action         | 不变                      |

**R1 为什么崩**：它第 1 步的 thought 里**已经写出了正确答案**，却选择了 `scroll`：

```
s1 scroll    thought=第一条名言是'The world as we have created it is a process of o...
s2 click e1  thought=找到第一条名言
s3 click e1  thought=找到第一条名言的作者信息   ← 点进作者页（els 55 → 4）
```

它给自己定了 `plan=['找到第一条名言','找到作者信息']`，然后把 plan 当成**必须走完的待办清单**，  
压过了「信息够了就 finish」这条最高优先规则。**一次改动换来 R3、赔掉 R1，净收益为零。**

**第二轮**：改两处措辞，都针对"plan 变成了闸门"这个根因——

1. 硬规则里把 plan 的定位写清楚：`plan 只是提醒别漏步骤，不是必须走完的清单；
   只要正文里能看到答案，立刻 finish —— 哪怕 progress 还没填满`
2. 渲染的「还剩 N 条」后面补一句 `plan 只是提醒，不是必须走完的清单：现在就能回答的话，直接 finish`
3. 加**示例 4**：给了 plan 但中途发现信息已足够 → 立刻 finish（直接对着 R2 的场景写的）

### 7.3 最终结果：25% → 50%

| 题  | 改前             | 改后                 | 变化                               |
| -- | -------------- | ------------------ | -------------------------------- |
| R1 | 3/3（1 步）       | ✅ 1 步              | 恢复                               |
| R2 | 0/3（12 步 loop） | ❌ 2 步，答 Mark Twain | **形态大改**：不再打转，落在正确的 page/2，但读错条目 |
| R3 | 0/3（3 步错答案）    | ✅ 2 步 André Gide   | **修复**，且比改前少 1 步                 |
| R4 | 0/3（7 步 loop）  | ❌ 3 步 loop         | 不变                               |

**2/4 = 50%**，两次连跑结果完全一致（同答案、同步数），确定性仍然成立。

三条有意思的细节：

1. **R1 的答案从「Albert Einstein」变成了「引言原文 + by Albert Einstein」**  
   —— 判定按"答案里是否含 einstein"通过，合法。但说明模型现在倾向于把读到的整段都搬出来
2. **R2 的新失败是真·阅读错误**：`Mark Twain` 是 page/2 的**第 9 条**（curl 确认  
   顺序为 Marilyn Monroe / J.K. Rowling / Albert Einstein / … / Mark Twain / Allen Saunders），  
   它却写"正文第一条就写着 by Mark Twain"。翻页这一步已经做对了，卡在"从长正文里挑出第几条"
3. **R3 只用 2 步**：改前 3 步（多点一次 Next），现在 1 步进标签页、1 步作答 ——  
   plan 的清单形式让它看清"还剩的是读作者，不是翻页"，正是设计意图

### 7.4 为什么 R2 会读错第 9 条（下一处要动的地方）

正文是一整块纯文本（`snapshot['text']`），10 条引言首尾相连。模型要自己把  
「引言正文」和「by 作者」对齐，还要数"哪一条在最前面"——弱模型做不到。

这不是提示词能解决的，得在**渲染层给正文加序号**（`[1] … by X`）。  
它和 R4 的元素截断问题同属"渲染层可读性"，可以合并成下一步（原选项 B 的扩展版）。

## 八、渲染层修复（正文结构与截断）

### 8.1 先纠正一个判断：R4 不是"元素截断"造成的

上一版我把 R4 的根因写成"元素上限 80 把搜索框挤掉了"。**取证之后发现这是错的。**

直接开浏览器数 MDN 首页：

```
共 83 个元素，列出 80 个
其中 input 类：0
页面真实 input/textarea 总数： 0
```

MDN 的搜索根本不是一个常驻输入框 —— 它是一个 button，点了才弹出输入面板，  
输入框是**之后才被创建**的。所以"截断把 input 挤掉"这个假设不成立，  
按这个假设去做"按相关性截断"等于修一个不存在的问题。

R4 的真实形态是：任务要求"在搜索框里搜索 X"，页面上没有可输入的框，  
模型退而求其次去点各种 button（`e2 是 button，不能往它里面输入文字`），然后在链接堆里打转。  
它考的是**多步交互的探索能力**（先点开搜索入口，等输入框出现），不是渲染问题。

**这一条单独记下来**：假设要先验证再动手，否则会花力气修一个幻影。

### 8.2 真正的问题：正文被压成一行，且截断位置切掉了唯一答案

`snapshot.py` 取正文原来是：

```js
const rawText = (document.body.innerText || '').replace(/\s+/g, ' ').trim();
```

`\s+` 把换行也压掉了 —— page/2 的整页文字变成 **1 行 1216 字符**。

再叠上"头 60% + 尾 40%"的截断，量一下全文字符下标：

| 位置       | 内容                               |
| -------- | -------------------------------- |
| 全文       | 3445 字符                          |
| **1108** | `by Marilyn Monroe` ← R2 的答案     |
| 3079     | `by Mark Twain` ← 模型答出的那个（第 9 条） |

上限 1200 → 头只有 720 → **答案被切在外面**；尾从约 2965 起 → Mark Twain 在 3079，  
**正好是拼接后的第一句**。模型于是非常合理地认为"正文第一条 = Mark Twain"。

它不是猜错，是**我们让它看不到**。

### 8.3 三处改动

| 改动   | 内容                                                         |
| ---- | ---------------------------------------------------------- |
| 保留换行 | 按行 split → 行内多空格压成一个 → 丢空行 → 换行 join                       |
| 截断策略 | 1.25 倍容差（轻微超限不切）；按行切但只允许退 30% 预算；接缝处明说「下一行直接是页面末尾，不是接着上面的」 |
| 上限   | `MAX_TEXT_CHARS` 1200 → **3000**（+ 1.25 = 3750，常见内容页整段放得下） |

改完后同一个页面：**截断=False，3445 字符，47 行，`by Marilyn Monroe` 在里面**。

### 8.4 结果

| 题  | v4                | v5                        |
| -- | ----------------- | ------------------------- |
| R1 | ✅ 1 步             | ✅ 1 步                     |
| R2 | ❌ 2 步答 Mark Twain | ✅ **2 步答 Marilyn Monroe** |
| R3 | ✅ 2 步             | ✅ 3 步                     |
| R4 | ❌ 3 步 loop        | ❌ 5 步 loop                |

**3/4 = 75%**，连跑两次完全一致。

### 8.5 剩下的 R4

R4 已经不是渲染问题，而是"页面上没有输入框，需要先点开搜索入口"。  
它要么靠更强的探索提示词，要么靠"点击后等新元素出现"的机制（现在的 `settle()` 只等固定 400ms）。  
这是另一个方向，不建议混在渲染层里做。

## 九、感知层修复（shadow DOM / 表单保底 / 弹窗聚焦）

### 9.1 先再纠正一次判断

第 8.1 节我写"R4 不是元素截断造成的"——这半句是对的，但结论只对了一半。  
当时的判断是"需要先点开搜索入口"，隐含假设是"入口在 light DOM 里，只是需要点击"。

取证之后发现更糟：**整个 light DOM 里 `input` 数量 = 0**，搜索入口和输入框  
全在 Web Component 的 shadow DOM 里。也就是说不是"要多点一步"，是**看得见的部分里根本没有**。

### 9.2 证据链

| 检查                                                   | 结果                                                         |
| ---------------------------------------------------- | ---------------------------------------------------------- |
| `document.querySelectorAll('input,textarea').length` | **0**                                                      |
| `<mdn-search-button>` shadow 内                       | `BUTTON title="Search the site"`（可见）                       |
| `<mdn-homepage-search>` shadow 内                     | `BUTTON text="Search"`（可见）                                 |
| `<mdn-search-modal>` shadow 内                        | `<dialog><form><input type="search" placeholder="Search">` |
| Playwright `[data-wp-id]` 能否命中 shadow 内元素            | **能**（且点击成功）                                               |

最后一条决定了修法：**动作层不用动，只修感知层**。

### 9.3 四处改动

| 改动                                     | 为什么                                                  |
| -------------------------------------- | ---------------------------------------------------- |
| 遍历 open shadow root（深度 ≤3）收集元素、清理编号    | 不穿 shadow 就等于看不见 Web Component 里的所有控件                |
| 表单控件保底占名额（上限一半，至少 10 个）                | 94 个候选只列 80 个时，shadow 里的输入框排在最后被切掉                   |
| `type` 放行 `combobox/searchbox/textbox` | MDN 写的是 `role="combobox"`，只认 input/textarea 会判"不能输入" |
| 弹窗打开时只列弹窗内元素 + 快照里明说                   | 弹窗外此刻真的点不到，列出来就是给模型挖坑                                |

第四条的实测对比很直接：

```
弹窗开着，无聚焦：元素 94 个 → 模型点了被遮住的 JavaScript 链接，
                  Playwright 报「<mdn-search-modal> intercepts pointer events」，重试 10s 超时
弹窗开着，有聚焦：元素 1 个（combobox Search）→ 直接输入，顺利往下走
```

### 9.5 这个 100% 意味着什么（别过度解读）

四道题是**自己选的真站点**，不是随机抽样。100% 说明的是：

- 这三类能力通了：静态提取、翻页、标签导航、前端渲染 + 多步搜索
- 感知层不再对 Web Component 免疫

它**不说明** Agent 能处理任意网站。已知未覆盖的：  
closed shadow root（规范限制，读不到）、iframe 跨域内容、Canvas/WebGL 渲染的界面、  
需要登录态的站点、无限滚动的长列表。下一步该主动找"能打败它的站"，而不是庆祝 100%。
